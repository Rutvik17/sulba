# Working on Sulba

Rules for Claude Code in this repository. They come from the founder and override defaults.

## Hard rules

- Work on a feature branch, never on `main`, and commit to it as you go. When every check passes and the work meets the standard, squash the branch into one commit, push it and open a pull request. One pull request builds one lab end to end, with all its stages. Any other work, such as setup or a platform feature, takes one pull request per task. The founder reviews and merges every pull request: never merge, push to `main` or rewrite its history.
- Commit messages have an imperative subject under 50 characters and a body only when the reason isn't obvious. Commits and pull request descriptions carry no attribution lines and no session links.
- Follow best practice without being asked: maintained libraries, strict types, tests for behaviour, no dead code. No filler in code, comments, docs or commit messages.
- Decide on evidence. A new architectural choice gets a record in `docs/decisions` with the options compared and the sources read. An accepted record is superseded, never rewritten.
- Secrets never enter the repository, issues or logs. They live in GitHub Actions secrets, Cloudflare Worker secrets, the Supabase dashboard or a gitignored `.dev.vars`. Never read `.dev.vars` or `.env` files.
- Only public keys reach the browser: the Supabase publishable key and the Turnstile site key.
- Learner data lives in Supabase, never in GitHub.

## Commands

| Command | What it does |
| --- | --- |
| `pnpm dev` | Runs the site at http://localhost:4321 in workerd |
| `pnpm lint` / `pnpm lint:fix` | Biome: formatting, lint rules, import order |
| `pnpm lint:python` | Ruff on the Python code: the lab's, the courses' and the tools' |
| `pnpm typecheck` | `astro check` at TypeScript's strictest settings |
| `pnpm test` | Vitest unit tests |
| `pnpm test:python` | The lab's Python tests, in CPython through uv |
| `pnpm check:content` | Every course's files against their schemas, and every stage in Pyodide and CPython |
| `pnpm check:references` | Every lab's references, recorded again by its `make.py` with the library it pins |
| `pnpm check:machine` | Every lab that runs on the learner's machine, run from its download through its runner, `sulba.py` |
| `pnpm test:db` | The database's migrations in a local Supabase, and the pgTAP tests of its row-level security (needs Docker) |
| `pnpm test:e2e` | Playwright end-to-end and axe accessibility tests in Chromium, Firefox and WebKit, on desktop and phone |
| `pnpm build` | Builds the site |

Run lint, lint:python, typecheck, test, test:python and check:content before calling work done, test:db when the database changes, check:references when a lab's references do, and check:machine when a lab that runs on the learner's machine, or its runner, does. On Windows, run the Python ones in Docker if uv isn't installed.

End-to-end tests are written with each feature, and run only when the founder asks. CI runs them on the first of each month and when started by hand (`e2e.yml`), never on a pull request or a push to `main`; fix anything a run shows broken in the next pull request.

## How the project is set up

- `apps/web` is Astro 7 on the Cloudflare Worker `web` (`wrangler.jsonc`). Pages are built ahead of time; a route renders on the server only when it must (decision record 1).
- Astro sessions are off and images are optimised at build time, so a deploy creates no KV namespace and no Images binding.
- `public/_headers` sends `X-Robots-Tag: noindex` everywhere until launch (Phase 5). At launch it comes off sulba.dev only; preview addresses keep it.
- CI runs once for every pull request and every push to `main`. When it passes, `main` deploys to sulba.dev, the site's only address, and a pull request from this repository gets a Worker Preview on workers.dev, which `preview-cleanup.yml` deletes when its branch is deleted. Dependency updates (`renovate/*`) and pull requests from forks are tested but not deployed.
- The contact form posts to `/api/contact`, which checks the Turnstile token and sends the message with Resend (decision record 12). Its four secrets are Worker secrets; without them it answers 503. Tests stand in for `/api/contact` and Turnstile, so no test ever sends mail.
- Cloudflare Web Analytics is set in the dashboard, so it's in no file here and local tests never see it. Cloudflare adds its script to every page except for visitors in the EU (Web Analytics on "Enable, excluding visitor data in the EU") and in the UK, Norway, Iceland, Liechtenstein and Switzerland (a Configuration Rule that disables Real User Monitoring), as decision record 13 sets out. Workers Logs are on too (`observability` in `wrangler.jsonc`).
- Cloudflare Access ("Previews only", set in the dashboard) puts every preview address behind sign-in, and sulba.dev stays public (decision record 9). Worker Previews need `preview_urls` on. Never turn it on in a Cloudflare account without that Access policy: it brings back every old preview address, and those can't be deleted.
- Dependencies are pinned to exact versions. pnpm refuses versions less than a day old and Renovate waits three days. TypeScript stays on 6 until `@astrojs/check` supports 7.
- GitHub Actions are pinned to commit SHAs with the version in a comment.
- Components live in `packages/ui`, a folder each: a CSS Module for the look, and a React component that takes its behaviour from React Aria Components (decision record 11). Astro pages put a component's classes on native elements and load no JavaScript; only a page with a React island loads React.
- `packages/editor` is the code editor: CodeMirror 6 with Python, Sulba's colour theme and 14 named after popular editor themes, and Ruff's checks and formatting in a Web Worker (decision record 14). On a page with an editor, the top bar's theme panel offers the editor themes too, and the browser keeps the one chosen.
- The gallery at `/gallery/` shows every component in each of its states. `astro dev`, the end-to-end tests and previews have it; sulba.dev doesn't (`apps/web/gallery.ts`). A new component, or a new state, joins the gallery and its screenshot tests in the same pull request.
- CI's Screenshots job compares the gallery with the pictures in `apps/web/screenshots`, taken in Playwright's Linux image; they never run on Windows. When the look changes on purpose, commit the new screenshots the failed job attaches (CONTRIBUTING.md).
- Every lab, and every model a lab uses, runs on the learner's device: in the browser, or on their machine, from a lab's download run with uv (decision records 25 and 28) or, for what uv can't install, through the `sulba` command. Sulba runs no learner code and no model, so there are no hosted models, cloud GPUs or certificates, and each level states the machine it needs before it begins (decision record 17).
- `packages/data` holds the database: migrations in `supabase/migrations` and pgTAP tests in `supabase/tests`, which CI runs in a local Supabase. Every table has row-level security, and a learner reads only their own rows. Progress is a log of attempts: the browser adds them, and Postgres folds them into each stage's progress and each day studied (decision record 18). The hosted project is on Supabase's free plan, which pauses a project after a week with too little use, so each day `database-check.yml` asks for every learner table without signing in: the requests keep it running, and each must be refused. A new learner table joins that list.
- Learners sign in with GitHub or Google through Supabase Auth, in the browser (decision record 19). Only `/sign-in/` and `/account/` load supabase-js; a lab's workspace, a course's page and `/review/` load it only when the browser holds a session. Signed in, the workspace sends each attempt from an outbox in local storage and takes in the stages passed on other devices once a visit, and `/account/` shows the days studied and the streak they make. A learner's code and plans never leave the browser. Supabase's address and publishable key default to the hosted project, and the end-to-end tests stand in for it, so no test reaches it.
- `packages/lab` runs a session's tests and speaks one protocol for every runner (decision record 17): files and tests go in, a result per test comes out. In the browser, Pyodide runs in a Web Worker, and a run past the time limit is stopped by ending the worker. A run's time starts once its packages are loaded and the modules its files import from them, such as `scipy.stats`, are imported, and what they leave alive is frozen out of garbage collection, so a run's collections pass over it. Both Pyodide and CPython call the same pytest plugin (`python/sulba_runner.py`), and the fixtures in `fixtures/` must give the same results in each. Its pytest fixtures are a plugin of their own (`python/sulba_fixtures.py`), which a run of the learner's own tests inside a test loads with `-p sulba_fixtures`. The `loop` fixture runs a test's asyncio code on a virtual clock (decision record 21), and a FastAPI app's tests send their requests in process through httpx on that loop, which also runs the app's `def` endpoints (decision record 24). The `typecheck` fixture gives mypy's errors in the session's files (decision record 22). Checks outside a browser run requests through `src/node.ts`: in Pyodide, or in CPython through uv. A lab that runs on the learner's machine downloads with `python/sulba.py` (decision record 28), which runs its stages there through the same plugin and prints a link back to the lab's page; the link's fragment carries the stages done and their attempts (`src/machine.ts` holds what the download tells it).
- `pnpm --filter @sulba/lab pyodide`, which `pnpm test` runs first, puts Pyodide's files together in `packages/lab/pyodide`: its core from npm, and each package's wheel, checked against the sha256 in Pyodide's lock file. CI's checks and content jobs keep that folder from run to run, checking each wheel against its sha256 again, and the deploy job starts without it. mypy needs two wheels Pyodide doesn't ship, which come from PyPI, checked against PyPI's sha256, and join the lock file the site serves (decision record 22). The site serves them at `/pyodide/<version>/` (`apps/web/pyodide.ts`), cached for good. The CPython packages in `packages/lab/python/uv.lock` are pinned to the versions Pyodide ships, and those two to the versions the site serves, and a test fails when they differ, so Renovate leaves them alone.
- Formulas in a course's prose are TeX, which Temml renders to MathML at build time, set in Noto Sans Math from `packages/ui/src/fonts` (decision record 15). Numbers in prose come from the stage's `figures.py`, never typed. Both the content check and the build fail on a formula that doesn't render, a tag inside code, a figure missing or never shown, figures that differ between Pyodide and CPython, or a character the math font can't draw. The build keeps each stage's figures in `node_modules/.cache/sulba-figures`, under a hash of its files, the runner and Pyodide's lock file, so a stage that hasn't changed doesn't run again. CI's checks job keeps that folder from run to run. The deploy job, which holds deploy credentials, starts without it, and the content check always runs every one.
- Courses are files in `courses/`, laid out as `courses/README.md` describes (decision record 7). `packages/content` reads them, checks them against their schemas, and builds each stage's runs: a stage's solution must pass its own and every earlier stage's tests, a Build, Ship or Problem stage's starter must fail at least one, and a Catch stage's problems must each be found by one hidden check (`courses/README.md`). A code model on the author's machine drafts a Catch stage's problems with `pnpm --filter @sulba/content draft`, and the author chooses among them. A lab that runs on the learner's machine runs its stages and figures in CPython alone, in its own project, which pins torch from PyTorch's CPU index, and CI's Machine labs jobs run its download through `uv run sulba.py` on Windows, macOS and Linux and fail when a stage's figures differ between them. Such a lab can fetch files too large for the site to serve, such as a dataset or a model's weights, from their publishers (`fetch` in `lab.yaml`, decision record 29): each is pinned by its size and sha256, `sulba.py` fetches it into the download's `data/` before the first run, and the checks keep it under its sha256 in `node_modules/.cache/sulba-fetched`. CI's Machine labs jobs keep that folder between runs, its checks, content and References jobs start from it, and the deploy job fetches every file again. A lab that builds what a library does checks the learner's code against the library's recorded results (decision record 27): its `references/make.py`, a script uv runs with the library pinned, records each case's inputs and results as JSON, which a run has at `references/<file>`, and CI's References job records them again and fails on a difference. make.py can read the lab's data, the files it fetches included (decision record 30).
- Each lab has a page at `/<course>/<module>/<lab>/`, built from `courses/` through a content collection (`apps/web/src/lib/labs.ts`). Its workspace is a React island that renders only in the browser: it keeps each stage's code, the stages passed, each finished Catch review and each Problem stage's start, plan and time in browser storage, opens a stage once the one before is passed, and runs the tests with `packages/lab`. A Problem stage is an interview problem against the clock (decision record 23): its brief shows once the learner starts, its editor once their plan is written, and its explanation and solution once it passes or its minutes are up. The page doesn't carry the lab's datasets or references: the site serves each at `/data/<hash>/<file>` or `/references/<hash>/<file>`, in a folder named for its text and cached for good, and the workspace fetches them once a visit. Each course has a page at `/<course>/`, which the home page and each of its labs link to (decision record 26): a card for the learner's next lab, then each level's facts, with the machine it needs (`needs` in `course.yaml`), and its modules, each a numbered row that shows its labs' titles and opens to their details. It shows how many of each lab's stages the learner has passed, in this browser and, signed in, in their account, and without JavaScript every module shows open. A lab can carry a project, and its workspace then has a Download: the project's files, the lab's data and the learner's files, zipped in the browser with fflate, for the learner to run with uv (decision record 25). The site serves a project's files like datasets, at `/project/<hash>/<file>`, and the content check holds each project's lock to Pyodide's versions. A lab whose stages need a package Pyodide doesn't ship, such as torch, runs on the learner's machine (`runs: machine` in `lab.yaml`, decision record 28): its page has no editor and loads no Python, its download carries its stages' tests and checks with the runner, and the link `uv run sulba.py` prints marks the stages done in this browser and, signed in, in the account. A build with `SULBA_COURSES` set reads courses from that folder instead; the end-to-end and screenshot tests use the content package's fixture course.
- A stage can have a chart: its `chart.py` draws with the learner's code, and the workspace's Chart tab shows the result in SVG, the solution's faded until the stage is passed (decision record 16). The content check draws each chart with the stage's solution, in Pyodide and CPython.
- A stage can have review cards (`cards.yaml`), which come back at `/review/` once the stage is passed (decision record 20). The browser keeps every review in local storage, signed in or not, and works out each card's schedule by replaying its reviews through FSRS with ts-fsrs, whose intervals the unit tests pin. Signed in, `/review/` takes in the account's passes and reviews once a visit, and sends the reviews the account lacks.
- The build phases (Phase 0 to Phase 6) are internal. Learners never see them.
- The pictures in `brand`, and the site's icons in `apps/web/public` (`favicon.ico`, `icon.svg` and `apple-touch-icon.png`), are drawn by `pnpm brand` (`apps/web/scripts/brand.ts`) from the mark, the avatar shapes and the design tokens. Change the script and run it again; never edit a picture by hand.
- One course at a time: AI Engineering is built end to end before any other course starts. A language's editor support and Docker image arrive with the first session that uses it.

## Correctness

Wrong content is worse than no content. Never claim certainty you don't have. These checks happen behind the scenes: no page ever tells learners how content is checked or computed.

- Every number, table and chart a learner sees is produced by code that runs in CI.
- Every from-scratch build is tested against a reference implementation, such as PyTorch or NumPy, within a stated tolerance.
- A claim code can't check is verified against a primary source (a paper, the official documentation) that was opened and read, not recalled.
- Versions, model names, APIs and prices are pinned and dated, and re-checked before each release.
- Before a level goes public, it is reviewed again against live sources.

## Product rules

- Learner-facing copy reads like a real course product: plain topic titles, standard section names (Brief, Hints, Explanation, Solution, Tests, Chart, Review) and short, direct sentences. Never describe how the site is made. No coaxing or teaser lines.
- Every number a learner sees can be traced to its inputs on the same screen.
- No referral schemes of any kind.
- Data and API providers, and the authors of code a lab ports, may be credited where their terms ask; teaching sources are not.
- The site never says its code is open source, and it doesn't link to this repository.
- The Privacy Policy and the Terms describe the site as built. A change to what the site collects, keeps in the browser or sends to a provider updates the Privacy Policy, and its date, in the same pull request.

## Documentation

- Each document has one purpose and one home: rules in this file, running and contributing in the README and CONTRIBUTING, decisions in `docs/decisions`. A fact lives in one place; other documents link to it.
- Documents cover the app, its architecture, principles and rules. Research notes, session history and explorations stay out; research appears only as a decision record's sources.
- Documents state what is decided, not what was ruled out. Options that were weighed appear only in the decision record that compared them.
- When the code or a decision changes, every document that mentions it changes in the same commit, and what no longer applies is deleted. Accepted decision records are the exception: they are superseded.
- A document is written when the thing it describes exists.

## On Windows

- Edit files with the editor tools, never by round-tripping text through PowerShell, which corrupts UTF-8.
- Files use LF line endings (`.gitattributes`). Never rewrite bytes across a folder tree.
