`mode("overwrite")` says only "Overwrite existing data", and on the day's own folder the old files go first, so a run that fails partway leaves the day with none. `append` would "Append contents of this DataFrame to existing data", so a day saved twice would have its trips twice, and `partitionBy("day")` with `overwrite` on the whole folder would overwrite every day's files to save one.

Writing elsewhere first keeps the old files until the new ones are complete. The new folder sits beside `folder`, on the same disk, since Python's `os.rename` "may fail if src and dst are on different filesystems", and "If successful, the renaming will be an atomic operation" on Linux and macOS. On Windows, "if dst exists a FileExistsError is always raised", so the old folder moves out before the new one moves in. A reader in that moment finds the day missing, never half written. `mkdtemp`'s caller "is responsible for deleting the temporary directory and its contents when done with it", which `finally` does whether the run succeeds or not.

Spark reads the folders' names as a column: "Spark SQL will automatically extract the partitioning information from the paths", and "the data types of the partitioning columns are automatically inferred". The same page says "When type inference is disabled, string type will be used for the partitioning columns", so the cast to a date makes `day` a date whatever the reader's settings.
