PySpark's testing guide makes the case for tests over looking at results: "One option is to simply eyeball the resulting DataFrame. However, this can be impractical for large DataFrame or input sizes. A better way is to write tests." Its examples build each test's input with `createDataFrame` from a few rows, as these tests do, so that each test shows one requirement and its expected result can be worked out by hand.

The checks are a small mutation test: each plants one plausible mistake, and a suite that passes on all of them doesn't hold the pipeline to that requirement. The mistakes sit at the edges a test of real data may never reach. A month can pass with no failed value and no day of exactly 1.0 mm, and a test of that month can't tell a pipeline that keeps failed values, or counts a day as wet only above 1 mm, from one that gets both right. A test's own input can put a value, a day or a borough exactly where the rule changes.

pytest gives each test what it needs to change the world around it and put it back: `tmp_path` provides "a temporary directory unique to each test function", and with `monkeypatch`, "All modifications will be undone after the requesting test function or fixture has finished", so pointing `weather.py` at another file lasts for one test.
