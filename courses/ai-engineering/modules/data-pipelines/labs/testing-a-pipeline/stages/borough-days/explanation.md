A join's `how` is "default inner", and an inner join keeps only the rows that match on both sides. Counting the trips and joining the weather to the counts would lose every borough and day without a pickup, Staten Island on {% $fig.empty_day %} among them, and the table would say nothing about that day rather than 0. So the grid comes first: `crossJoin` "Returns the cartesian product with another DataFrame", 31 days by {% $fig.boroughs %} boroughs, {% $fig.rows %} rows, and left joins hang the counts and the weather on it, so every row stays whether anything matched or not.

A left join leaves an unmatched row's new columns null. That is right for the weather, which wasn't measured, and wrong for the trips, which were counted and came to none, so only `trips` is coalesced to 0. `wet` follows the rain: "Normal comparison operators return `NULL` when one of the operand is `NULL`", so a day without weather is neither wet nor dry.

`spark.range` makes the days without a file to read them from: it creates "a DataFrame with single pyspark.sql.types.LongType column named id, containing elements in a range from start to end (exclusive)". `date_format` takes Spark's datetime patterns, in which `E` is the day-of-week, and "Exactly 4 pattern letters will use the full text form".
