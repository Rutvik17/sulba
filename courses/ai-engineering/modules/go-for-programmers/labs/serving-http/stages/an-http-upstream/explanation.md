Every answer's body is the caller's to close. net/http's docs: "The caller must close the response body when finished with it", and "The default HTTP client's Transport may not reuse HTTP/1.x "keep-alive" TCP connections if the Body is not read to completion and closed". A gateway that left each body open would hold a connection open for every call it made, and open a new one for the next. `defer response.Body.Close()` right after the error check closes it on every way out, error answers too.

The context bounds the whole call. For a client's request, "the context controls the entire lifetime of a request and its response: obtaining a connection, sending the request, and reading the response headers and body." When the caller of `Chat` gives up, the request stops wherever it is, and `Do` or the decoder gives the context's error. The client has a deadline of its own only if it's given one: `http.DefaultClient` is `&Client{}`, and of its `Timeout`, "A Timeout of zero means no timeout." The gateway passes one client to every upstream, as the docs advise: "Clients and Transports are safe for concurrent use by multiple goroutines and for efficiency should only be created once and re-used."

A model server is a program the gateway doesn't control, and a broken one can answer with anything. `io.LimitReader` caps what the gateway reads at a megabyte for a reply and 4 kB for an error, so one bad answer can't take the gateway's memory. An error's text goes into the `StatusError`, never to the caller: `WriteError` gives the caller only the gateway's own words.

RFC 9110 defines `Retry-After` as "HTTP-date / delay-seconds". The upstreams the gateway asks send seconds, so `Chat` reads those, and a date or anything else counts as no wait. The wait goes to `Retry`, which waits at least that long before it asks again.
