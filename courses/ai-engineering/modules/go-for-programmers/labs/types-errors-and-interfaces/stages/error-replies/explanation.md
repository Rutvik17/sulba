Each status says whose problem it is. A 400 or a 404 is the caller's, and its message is the gateway's own, which says what to fix. The rest belong to the gateway's side, and RFC 9110 defines the two a gateway has of its own: a 502 means "the server, while acting as a gateway or proxy, received an invalid response from an inbound server it accessed while attempting to fulfill the request", and a 504 that it "did not receive a timely response from an upstream server it needed to access in order to complete the request."

An upstream's message isn't the gateway's to pass on. It can name the upstream's address, a key it was given, or the software it runs, and OWASP's cheat sheet on error handling: "Using error messages that do not provide implementation details is important to avoid information leakage." Its advice is the shape `WriteError` has: "a generic response is returned by the application but the error details are logged server side for investigation, and not returned to the user." A 400 from an upstream is still the caller's to fix, so it stays a 400, in the gateway's words.

429 means the caller is asking too fast, and RFC 6585, which defines it, says the answer "MAY include a Retry-After header indicating how long to wait before making a new request." RFC 9110 has its value as either a date or "a non-negative decimal integer, representing time in seconds." A wait of 3.1 seconds becomes 4: rounded down, the caller would come back before the upstream is ready. The gateway answers 429 only when every upstream was busy. With one busy and one down, waiting wouldn't fix the one that's down.

`errors.Is` and `errors.AsType` each look for one match in an error's tree, which the `errors` package describes: "Successive unwrapping of an error creates a tree." The soonest wait needs every `*StatusError` in it, so `WriteError` walks the tree itself. The package says an error wraps another "if e's type has one of the methods" `Unwrap() error` and `Unwrap() []error`. A type switch on those finds each child, whether `fmt.Errorf` or `errors.Join` made it.

The status goes out with the headers, and net/http's `ResponseWriter` warns: "Changing the header map after a call to ResponseWriter.WriteHeader (or ResponseWriter.Write) has no effect". `Content-Type` and `Retry-After` are set first.
