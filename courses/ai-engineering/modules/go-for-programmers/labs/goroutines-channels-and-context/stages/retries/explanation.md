Backing off gives a struggling upstream fewer calls the longer it struggles: each wait twice the last, up to `Max`. Waits alone still bunch up. Clients that failed together retry together, and AWS's architecture blog on backoff, which simulated many clients at once, puts the answer in two sentences: "The solution isn't to remove backoff. It's to add jitter." Random waits "spread out the spikes to an approximately constant rate." `Jitter` is a function the caller passes in, such as `func(d time.Duration) time.Duration { return rand.N(d) }` from `math/rand/v2`, a wait anywhere from none to the delay, while a test passes one that does the same thing every time.

An upstream that answers 429 or 503 can say how long to wait, and RFC 9110's `Retry-After` is "how long the user agent ought to wait before making a follow-up request." `Retry` waits at least that long: calling sooner asks a server that has already said it isn't ready.

`ctx.Deadline()` "returns the time when work done on behalf of this context should be canceled". A wait that would end past it would spend the caller's last moments asleep, then make a call that can't finish, so `Retry` gives up at once and the caller gets its answer sooner. A `select` on the timer and `ctx.Done()` ends a wait early when the caller goes.

`Delay` stops doubling before it overflows. A `time.Duration` is "an int64 nanosecond count", which "limits the largest representable duration to approximately 290 years": doubling a second 34 times passes it, and the wait would wrap round to a negative number, so the retries would come at once.
