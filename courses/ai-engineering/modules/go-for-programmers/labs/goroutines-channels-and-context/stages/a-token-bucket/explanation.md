A token bucket is the Go project's own rate limiter's shape: `golang.org/x/time/rate` says its `Limiter` "implements a "token bucket" of size b, initially full and refilled at rate r tokens per second." The burst lets a key send a few requests at once, and the rate holds it to its share over time. The gateway's bucket adds the tokens a request's wait has earned when it's asked, rather than on a timer, so a bucket nobody uses costs nothing.

Many goroutines ask the same bucket, and the Go memory model is blunt about it: "Programs that modify data being simultaneously accessed by multiple goroutines must serialize such access." Two calls that each read one token left and then took it would let two requests through on one token. `sync.Mutex` "is a mutual exclusion lock", so one call at a time reads and writes the tokens, and `defer b.mu.Unlock()` unlocks on every way out. A mutex "must not be copied after first use", which is why every method has a pointer receiver and `NewBucket` gives a `*Bucket`: a value receiver would lock a copy, and `go vet` reports that copy. The limiter's map needs the lock too. The Go FAQ: "Map access is unsafe only when updates are occurring", and the first request for a key adds to it.

`Wait` can't hold the lock while it waits, or every other caller would wait behind it. It works out when the next token is due, unlocks, and waits in a `select`, which goes on with whichever of its channels is ready first: the timer's, or `ctx.Done()`, which is closed when the caller is done. When the timer wins, `Wait` locks and looks again, since another caller may have taken that token first.

The tests run in a `synctest` bubble. Its docs: "Within a bubble, the time package uses a fake clock", and "Time in a bubble only advances when every goroutine in the bubble is durably blocked." A test that sleeps an hour runs at once, and a wait comes out the same on every machine, to the nanosecond.
