Effective Go: "A buffered channel can be used like a semaphore, for instance to limit throughput." A gate of `n` is a channel with room for `n` values. Each call sends one before it starts, a send that waits while the channel is full, and receives one when it's done, so no more than `n` run at once and `len(g.slots)` is how many are running. The wait is a `select`, so a caller that gives up while it waits for room leaves the queue at once, rather than waking later to work for nobody. The place goes back in a `defer`: the spec says that when a function panics, "Any functions deferred by F are then executed as usual", so a panic can't keep its place forever and shrink the gate.

`sync.WaitGroup`'s `Go` "calls f in a new goroutine and adds that task to the WaitGroup", and `Wait` waits for every one. Its docs add what makes the replies safe to read: "the return from f "synchronizes before" the return of any Wait call that it unblocks." Each goroutine writes only its own element of `replies`, so no two write the same memory, and after `Wait` every write is in place. Each goroutine has its own `i` and `request`, too: since Go 1.22, "each iteration of the loop creates new variables, to avoid accidental sharing bugs."

The first failure ends the batch. `context.WithCancelCause` gives a cancel that takes an error: "Calling cancel with a non-nil error (the "cause") records that error in ctx; it can then be retrieved using Cause(ctx)." The first failed request cancels the rest with its own error, the others stop with `context.Canceled`, which doesn't replace it, and `ChatAll` waits for them all before it returns, so no goroutine of its outlives the call.
