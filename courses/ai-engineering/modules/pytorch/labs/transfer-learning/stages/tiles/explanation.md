A zip lists its folders in the order they were added to it, and this one lists {% $fig.first_listed %} first, where sorted names put {% $fig.first_sorted %}. Numbered in the zip's order, {% $fig.moved %} of the {% $fig.kinds %} kinds would take other numbers than sorted names give them, and a model trained with one numbering would have its answers read as the wrong kinds with the other. Sorted names give each kind the same number from any copy of the tiles. Picking from sorted names does the same for a split: the tiles picked depend only on their names and the seed.

The kinds have from {% $fig.fewest %} tiles to {% $fig.most %}, the fewest in {% $fig.smallest %}. Tiles picked from all the kinds at once would come in those shares, and give the smallest kinds the fewest labels. Picking as many of each kind, as the survey labels them, gives every kind as many tiles to be learned from. With as many test tiles of each kind, accuracy weighs every kind the same, and a classifier that always gives one kind is right on {% $fig.chance %} of them: the floor any classifier must clear. The two parts share no tile, since a tile tested on after it was learned from says nothing about tiles not yet seen.

Pillow, like NumPy, keeps a picture's pixels as rows, then columns, then channels. PyTorch's layers take a batch as `(N, C, H, W)`, with the channels first, which `permute` gives. A JPEG can hold one channel of greys as well as three of colour, and `convert("RGB")` gives three either way. A tile of another size would cover another area of the ground, so it's refused rather than resized.

Read whole, the tiles take {% $fig.bytes_mb %} as bytes, and {% $fig.float_gb %} as `float32`, so the lab reads only the tiles it uses, straight from the zip.
