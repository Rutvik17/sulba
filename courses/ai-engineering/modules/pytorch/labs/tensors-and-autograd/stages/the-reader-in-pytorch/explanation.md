The port reads each of the {% $fig.test %} test digits as the NumPy reader does, {% $fig.accuracy %} of them right, because it does the same arithmetic in the same order: the same start and batches from `rng`, the same scaling, and the same {% $fig.steps %} steps in `float64`. The two differ only in the order some sums add up their terms, which moves the last digits of a number and no reading. A port started instead from `torch.manual_seed(0)` and `nn.Linear`'s own weights, and trained the same way, reads {% $fig.torch_right %} of the test digits right, but {% $fig.torch_differ %} of them differently from the NumPy reader, and fails the office's comparison.

Reading under `torch.no_grad()` keeps autograd from recording anything, so no tensors are kept for a backward pass that never comes. `torch.inference_mode()` does the same and more: tensors made inside it can never join a graph later, which lets PyTorch skip the bookkeeping that would allow it.
