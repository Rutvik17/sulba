Java's threads run at once, on every core. CPython's threads, by default, take turns: its global interpreter lock is "the mechanism used by the CPython interpreter to assure that only one thread executes Python bytecode at a time", which makes "critical built-in types such as dict implicitly safe against concurrent access". Java has no such lock, so `HashMap`'s docs say "if multiple threads access a hash map concurrently, and at least one of the threads modifies the map structurally, it must be synchronized externally." Two threads adding 1 to the same count can both read 41 and both write 42, and two threads adding keys at once can leave the map itself broken. Even a plain `long` field isn't safe: "a single write to a non-volatile long or double value is treated as two separate writes: one to each 32-bit half."

`java.util.concurrent` has the pieces, and `ConcurrentHashMap`'s docs put them together for this exact job: "A ConcurrentHashMap can be used as a scalable frequency map (a form of histogram or multiset) by using LongAdder values and initializing via computeIfAbsent", as `freqs.computeIfAbsent(key, k -> new LongAdder()).increment();`. `computeIfAbsent` matters for a page no one has counted yet: "the entire method invocation is performed atomically", and "the supplied function is invoked exactly once per invocation of this method if the key is absent", so sixty-four threads counting a new page's first question all get the same counter. Checking `containsKey`, then putting a counter, lets two threads each put one, and the second throws away the first one's count. `LongAdder` "is usually preferable to AtomicLong when multiple threads update a common sum that is used for purposes such as collecting statistics", and "under high contention, expected throughput of this class is significantly higher", because it spreads the additions over several cells and adds them up when read.

The dashboard reads while the threads write. A `HashMap`'s iterator would throw a `ConcurrentModificationException`, or worse, see a map mid-change. `ConcurrentHashMap`'s iterators "return elements reflecting the state of the hash table at some point at or since the creation of the iterator/enumeration. They do not throw ConcurrentModificationException." A report reads each counter once into a new `EnumMap` or list, so it holds the counts as they stood, and later questions change only the counters. Keeping the total in its own `LongAdder` means it only ever goes up.

The tests run their threads as virtual threads. JEP 444 introduced them as "lightweight threads that dramatically reduce the effort of writing, maintaining, and observing high-throughput concurrent applications": a server can give each request a thread of its own, ten thousand at a time, where an operating system thread each would cost too much. They run on a few carrier threads, one per core, so the races are as real as on any other threads, and a counter that's right under ten thousand of them is right under the requests of a busy day.
