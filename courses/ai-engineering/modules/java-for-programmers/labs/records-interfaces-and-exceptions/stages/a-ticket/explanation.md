A record is Java's dataclass with `frozen=True`. The Java Language Specification calls it "a restricted kind of class that defines a simple aggregate of values", and JEP 395, which added records, calls them "classes that act as transparent carriers for immutable data." The header, `(String id, Service service, Status status, String summary)`, gives the record its private final fields, an accessor for each, such as `id()`, a constructor, and `equals`, `hashCode` and `toString`. `Record`'s docs say what the generated `equals` does: it "returns true if and only if the argument is an instance of the same record class as this record, and each component of this record is equal to the corresponding component of the argument". So two tickets with the same parts are equal, as two equal dataclasses are.

The compact constructor is where a record checks its values. The specification: "The intent of a compact constructor declaration is that only code to validate or normalize parameters needs to be given in the constructor body; the remaining initialization code is supplied by the compiler." Its body sees the parameters, not the fields, and "after the last statement, if any, in the body of the compact constructor has completed normally, all component fields of the record class are implicitly initialized to the values of the corresponding formal parameters." That's why `summary = summary.strip();` keeps the stripped summary: it changes the parameter, which then sets the field. An exception thrown from the body means no ticket is made at all, so no code anywhere holds a ticket with a bad id.

Any reference in Java can be `null`, as any name in Python can be `None`, and the compiler doesn't stop it, so the ticket refuses `null` itself. `Objects.requireNonNull` "is designed primarily for doing parameter validation in methods and constructors", and its message names the part. The two exceptions say different things: a `NullPointerException` for a part that's missing, and an `IllegalArgumentException`, which the docs describe as "thrown to indicate that a method has been passed an illegal or inappropriate argument", for a part that's there but wrong. Both are unchecked, since a bad ticket is the caller's mistake to fix, not a case the caller plans for.

A record can't change, so `closed()` makes a new ticket with the new status, as `dataclasses.replace` does. Everything that held the open ticket still holds it, open. `Status` is declared inside `Ticket`, and the specification says "a nested enum class is implicitly static", so it's `Ticket.Status` everywhere and needs no ticket to exist.

Jackson reads and writes a record through its components, and the names it uses are Java's unless an annotation says otherwise. `@JsonProperty("ticket")` names the `id` component, and on an enum's constants, its docs say it may "be used to change serialization of Enum", as `@JsonProperty("theFirstValue") THE_FIRST_VALUE`. Jackson also finds getters by their names, and Jackson's `MapperFeature` says that for a record, by default, "public getter methods following JavaBean conventions may be auto-detected, which may include helper methods that are not Record components." `isOpen()` is one of them, so without `@JsonIgnore` every ticket would gain a fifth field, `open`. `line()` and `closed()` don't start with `get` or `is`, so Jackson leaves them alone.

Reading JSON calls the same constructor, so a ticket from JSON is checked as one made in Java is. When the constructor throws, Jackson throws a `DatabindException`, here a `ValueInstantiationException`, whose cause is the ticket's own exception: the desk's API can answer with the ticket's message, and still know the request's JSON was at fault.
