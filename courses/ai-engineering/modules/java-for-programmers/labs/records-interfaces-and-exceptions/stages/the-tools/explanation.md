An interface with one abstract method is a functional interface, and a lambda can be one. The specification: "A functional interface is an interface that is not declared sealed and has just one abstract method (aside from the methods of Object), and thus represents a single function contract." `Action<A>` is one, so `arguments -> desk.listTickets(arguments.status())` is an `Action<ListTickets>`. Java has `Function<T, R>` already, but its `apply(T t)` declares no exception, so a lambda that calls `bookCallback` couldn't be a `Function`: `Refused` is checked, and the compiler would make the lambda catch it. `Action` declares `throws Desk.Refused`, so a tool's action passes the refusal up to `call`, which turns it into text.

A tool's arguments are a record, and its class is passed as a value, `Class<A>`, because Java's generics exist only for the compiler. Java's tutorial on type erasure says the compiler will "replace all type parameters in generic types with their bounds or Object if the type parameters are unbounded", so inside `Tools`, `A` is just `Record` at run time. `new A()` and `A.class` don't compile, and the tutorial gives the way round: "you can create an object of a type parameter through reflection", from a `Class<E>`. Jackson takes the class for the same reason: `treeToValue(node, tool.arguments())` needs to know which record to make. The bound, `A extends Record`, lets `Tools` ask the class for its components with `getRecordComponents()`, which "returns an array of RecordComponent objects representing all the record components of this record class", "in the same order that they are declared in the record header", which is the order the errors list them in.

`Tools` holds a `List<Tool<?>>`: tools of different records, so no one type fits them all. The `?` says "some record", but the code can't name it, so it can't pass a tool's record to that same tool's action. Java's tutorial calls the fix a helper method: "You can fix it by writing a private helper method which captures the wildcard." Inside `<A extends Record> String call(Tool<A> tool, ...)`, the compiler infers the `?` as `A`, and `tool.action().run(read)` takes the `A` that `treeToValue` gave.

The errors come in the order a model's mistakes would be found. Reading into a tree first lets the code tell a missing key from a key it doesn't know, and say which, before Jackson reads the record. Jackson's own errors then cover a value its field can't hold: an enum it doesn't have, a date that isn't one, a word for a number. Each is a `DatabindException` with the path to the value. A `ValueInstantiationException` is a `DatabindException` too, so the `catch` for it comes first. Java runs "the first (leftmost) such catch clause" that matches, and the other order doesn't compile: "It is a compile-time error if a catch clause can catch an exception class E1 and a preceding catch clause of the immediately enclosing try statement can catch E1 or a superclass of E1."

`call` catches `Refused` and no more. A refusal is part of the conversation: the model reads why, and calls again or tells the caller. A `NullPointerException` from inside an action is a bug, and turning it into text would hand the model a message about the code, and hide the bug from whoever runs the desk.
