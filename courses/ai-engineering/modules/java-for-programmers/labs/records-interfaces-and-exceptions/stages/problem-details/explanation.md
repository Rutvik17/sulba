A problem details object is the error format RFC 9457 defines for HTTP APIs, and the desk uses its simplest form. Its type is `about:blank`, which "indicates that the problem has no additional semantics beyond that of the HTTP status code", and then "the title SHOULD be the same as the recommended HTTP status phrase for that code (e.g., "Not Found" for 404, and so on)". The phrases are RFC 9110's, which renamed two of the older ones: it calls 413 "Content Too Large", since "the terms "payload" and "payload body" have been replaced with "content"", and it brought in 422 "(previously defined in Section 11.2 of [WEBDAV])" as Unprocessable Content. 429 isn't in RFC 9110 at all: RFC 6585 defines it, for a user who "has sent too many requests in a given amount of time". A client that reads `title` reads the phrase its HTTP library knows, so an old name is a small break between the desk and its callers.

The detail is for the caller. RFC 9457 says it "ought to focus on helping the client correct the problem, rather than giving debugging information." A refusal's message does that: it says why, and what the caller can do. An exception's message from anywhere else in the code can hold a connection string, a path on the server or a query, which a caller has no use for and an attacker has every use for, so a 500 says only that the server failed, and the message goes to the service's logs.

`InvalidDefinitionException` is a `DatabindException` too, which is why it needs its own row first: Jackson throws it when a type can't be read at all, such as a record with a `Runnable` in it, and that's the code's mistake. Answering it with 422 would tell the caller to change a request that was never the problem. A `switch` over types takes the first case that matches, as a `catch` does, and Java enforces the order: "It is a compile-time error if any switch label in a switch block is dominated", where a label is dominated when "one of the preceding switch labels would also apply". A case for `DatabindException` before `InvalidDefinitionException` doesn't compile.

Errors arrive wrapped. When a task fails, `CompletableFuture.join()` "throws an (unchecked) CompletionException with the underlying exception as its cause", and code that catches a checked exception and throws an unchecked one passes it on as the cause. `getCause()` "returns the cause of this throwable or null if the cause is nonexistent or unknown", so following it to `null` finds the error at any depth. The solution also stops at a cause it has seen, since `initCause` can make two exceptions each other's cause.

The pointer follows RFC 6901, where "'~' needs to be encoded as '~0' and '/' needs to be encoded as '~1'". The order matters: escaping `/` first would turn a key `a/b` into `a~1b`, and escaping `~` after it would make that `a~01b`, which reads back as `a~1b`. RFC 9457's own example puts its pointers in URI fragments, as `"pointer": "#/age"`, and RFC 6901 says a pointer goes into a fragment "by encoding it into octets using UTF-8, while percent-encoding those characters not allowed by the fragment rule in [RFC3986]". RFC 3986's rule is `fragment = *( pchar / "/" / "?" )`, which allows letters, digits, `-._~`, `!$&'()*+,;=`, `:` and `@` besides. Keys come from the caller's JSON, so they can hold anything: a space becomes `%20`, a `%` becomes `%25`, and `é`, two bytes in UTF-8, becomes `%C3%A9`.
