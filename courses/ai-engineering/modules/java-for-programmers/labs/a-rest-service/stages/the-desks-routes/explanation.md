A server made with `HttpServer.create` finds the handler for each request by its path: "the context whose path is the longest matching prefix of the request URI's path." A context takes every path that starts with its own, and the docs warn that one such as `/foo` "would match requests with a path of "/foobar" or "/foo/bar"." So the API takes every request, at `/`, and decides for itself what each path is, matching the whole path with a pattern. A path no context takes gets the server's own answer: "Any request for which no handler can be found is rejected with a 404 response", and that 404 is a page of HTML, not the problem details the desk's callers read.

An exchange is one request and its reply, answered in a fixed order: the headers set, then `sendResponseHeaders` with the status and the body's length, then the body. A length above zero "specifies an exact number of bytes to send and the application must send that exact amount of data", so the handler turns the JSON into bytes first and counts those: a character such as `é` takes two bytes in UTF-8. Then the exchange must end: "When the response body has been written, the stream must be closed to terminate the exchange." `HttpExchange` is `AutoCloseable`, so `try (exchange)` closes it however the handler ends, an exception included. The Java Language Specification says a try-with-resources statement's resources are "closed automatically, in the reverse order from which they were initialized, after execution of the try block."

The statuses are HTTP's own, as RFC 9110 defines them. For a 405, "The origin server MUST generate an Allow header field in a 405 response containing a list of the target resource's currently supported methods." For a 201, "The primary resource created by the request is identified by either a Location header field in the response or, if no Location header field is received, by the target URI." The target of `POST /tickets` is every ticket, so the new ticket's own address goes in `Location`. A 415 means "the origin server is refusing to service the request because the content is in a format not supported by this method on the target resource." A media type's name is the same in any case, and it can carry parameters such as `charset`, so the API compares only the part before any `;`, ignoring case.

Jackson 3 reads loosely unless it's told otherwise. Of the feature that refuses a field a record doesn't have, Jackson's source says: "Feature is disabled by default as of Jackson 3.0 (in 2.x it was enabled)." A field that's missing is read as null, and `FAIL_ON_NULL_CREATOR_PROPERTIES`, which refuses that, is off by default too. So the API's mapper turns both on, and a request with `"urgent": true`, or with no `summary`, gets a 422 that says where, rather than a ticket opened without a summary or a field quietly dropped. A time with seconds, `09:00:30`, would read as a `LocalTime` too, so `@JsonFormat(pattern = "HH:mm")` on the record's component holds it to hours and minutes.

A server given an executor, as the tests give it one, runs each request on a thread of its own, so two callers can open a ticket at the same moment. `Desk` keeps its tickets in an `ArrayList`, whose docs say: "If multiple threads access an ArrayList instance concurrently, and at least one of the threads modifies the list structurally, it must be synchronized externally." Two `openTicket` calls at once can both read the same count and give out `T-3001` twice, or lose a ticket as both grow the list. "A synchronized statement acquires a mutual-exclusion lock on behalf of the executing thread, executes a block, then releases the lock. While the executing thread owns the lock, no other thread may acquire the lock." The API holds the desk's lock for its reads too: a read and a write in two threads that no lock orders are what the specification calls a data race, and "When code contains a data race, counterintuitive results are often possible."
