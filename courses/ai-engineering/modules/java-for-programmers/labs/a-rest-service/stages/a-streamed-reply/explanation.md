A reply's length isn't known until the agent has finished it, and the caller should read it as it's written, so the reply is sent in chunks. `sendResponseHeaders` with a length of zero does that: "If the response length parameter is zero, then chunked transfer encoding is used and an arbitrary amount of data may be sent. The application terminates the response body by closing the OutputStream." The stream keeps what's written until it has enough to send, though, and a piece of the reply that sits there is a caller watching nothing. `flush()` is "an indication that, if any bytes previously written have been buffered by the implementation of the output stream, such bytes should immediately be written to their intended destination", so the handler flushes after each event.

Each event is a few lines of the format the HTML standard defines for server-sent events, of the media type `text/event-stream`. An `event:` line names it, a `data:` line carries it, and "If the line is empty (a blank line)", the reader is to "Dispatch the event". A `data:` line ends at a line break, and JSON writes a line break inside a string as `\n`, so one JSON value is always one line. The standard also says: "Event streams in this format must always be encoded as UTF-8."

The agent's events are a sealed interface, which permits only `Text`, `Tool` and `Done`. That lets the handler's `switch` over an event list one case for each, with no `default`. The Java Language Specification: "A default label is permitted, but not required, in the case where the switch block exhausts all the permitted direct subclasses and subinterfaces of an abstract sealed class or sealed interface." Of a `switch` statement with patterns, it says that it "must be exhaustive", so if the agent gained a fourth kind of event, the handler would stop compiling until it said what to send for it, rather than send nothing.

The limit is on the whole reply, not on each wait. A reply that sent a piece every second for an hour would never wait more than a second, so the handler keeps one deadline from `System.nanoTime()`, which "can only be used to measure elapsed time and is not related to any other notion of system or wall-clock time": a clock that jumps when the computer's time is set would cut a reply short, or let it run on. Each `next` gets what's left of the deadline.

The gate's place is the scarcest thing the service has, so it goes back in a `finally`, and the reply is closed by its `try`, whichever way the reply ends. The way it's easiest to forget is the caller hanging up. Nothing tells the handler then, but its next write throws an `IOException`, which passes out through both blocks: the reply is closed, the agent stops writing to no one, and the place goes to the next caller in line. A handler that gave the place back only after its loop would lose one for every caller who hung up, and once they were all gone, turn everyone away.
