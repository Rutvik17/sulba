Python's gate counted the callers in its line with a plain integer, which was safe on one event loop: nothing else ran between two lines of its code without an `await`. Java's callers are threads, any of which can run at any moment, so both counts need a class made for that. A `Semaphore` is one: it "maintains a set of permits. Each acquire() blocks if necessary until a permit is available, and then takes it. Each release() adds a permit, potentially releasing a blocking acquirer." Its docs give the use this gate makes of it: "Semaphores are often used to restrict the number of threads than can access some (physical or logical) resource."

The gate needs two counts. The running places are one semaphore, which callers wait on. Who's inside the gate, running or in line, is another, with a permit for every place of both kinds. A caller takes that permit with `tryAcquire()`, which "will return immediately with the value false" when there's none, and that `false` is a full line: the caller is turned away at once rather than waiting to be told to wait.

Order matters to a caller in line. A semaphore made without fairness "makes no guarantees about the order in which threads acquire permits. In particular, barging is permitted, that is, a thread invoking acquire() can be allocated a permit ahead of a thread that has been waiting". So a caller back for a second reply the moment theirs ended could take the place from someone who'd waited a minute. Made with `true`, "the semaphore guarantees that threads invoking any of the acquire methods are selected to obtain permits in the order in which their invocation of those methods was processed (first-in-first-out; FIFO)." The docs advise it for this kind of use: "Generally, semaphores used to control resource access should be initialized as fair, to ensure that no thread is starved out from accessing a resource." The count of who's inside needn't be fair, since no one waits on it: "the untimed tryAcquire methods do not honor the fairness setting, but will take any permits that are available."

A caller who hangs up while waiting is a thread that's interrupted. `acquire()` then throws: if the thread "is interrupted while waiting for a permit, then InterruptedException is thrown and the current thread's interrupted status is cleared", and it takes no permit. The caller did take a place in line, though, so `enter()` gives that back before it throws. Without that, every caller who left would keep a place in line for good, and a gate with a line of four would turn everyone away after four hang-ups. `enter()` throws the `InterruptedException` on rather than catching it, so the request's thread still learns it was told to stop.

`Busy` is a checked exception, as the desk's `Refused` was: a caller turned away is a case the code that calls `enter()` must answer, with a 503. RFC 9110 says a 503's "server MAY send a Retry-After header field (Section 10.2.3) to suggest an appropriate amount of time for the client to wait before retrying the request", and a delay there "is a non-negative decimal integer, representing time in seconds." A whole number of seconds that rounded a limit of 2.5 seconds down to 2 would tell callers to come back before any running reply has to end, so the gate rounds up.
