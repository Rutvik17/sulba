Each problem passed the assistant's tests because each test sent one request at a time, a `GET` with no body, to an address the server has, as the load balancer's health check does.

The server had no executor, and `setExecutor`'s docs say what that means: "a default implementation is used, which uses the thread which was created by the start() method." That one thread takes each request off the network and runs its handler, so while a handler waits, nothing else happens. A reply streams for a minute, and a caller on a slow phone connection sends a ticket's body a few bytes at a time; either holds the thread, and every other caller, the health check included, waits behind them. JEP 444, which brought virtual threads to Java, names the style this server needs: "it makes sense for an application to handle a request by dedicating a thread to that request for its entire duration", and virtual threads make that cheap: "Virtual threads are cheap and plentiful, and thus should never be pooled: A new virtual thread should be created for every application task." `Executors.newVirtualThreadPerTaskExecutor()` does that for each exchange.

The log's filter read the body to count its bytes. A `Filter` runs "before the application's exchange handler is invoked", on the same exchange, and of `getRequestBody()`, the docs say: "Multiple calls to this method will return the same stream." A stream read to its end has nothing left, so the API read an empty body, which Jackson refused, and every `POST` got a 422. The request's `Content-Length` header says how many bytes the caller sent without reading them. A filter that must count the bytes themselves can wrap the body in a stream that counts as the handler reads it: `setStreams` is "Used by Filters to wrap either (or both) of this exchange's InputStream and OutputStream".

`problem` wrote the body and returned, leaving the exchange open, while the health check's 200 closed its stream with `try`. The docs: "When the response body has been written, the stream must be closed to terminate the exchange." The server keeps what's written until the stream is closed or full, so the caller of `/healthz` got nothing, and waited. The load balancer asks only `GET /health`, which is why the bug stayed hidden, but a person checking by hand, or a monitor set up with a typo, would have seen the desk hang.

The API was the context for `/tickets` alone. A request goes to "the context whose path is the longest matching prefix of the request URI's path", and a path no context's path starts, such as `/`, gets the server's own answer: "Any request for which no handler can be found is rejected with a 404 response." That 404 is a page of HTML, which the chat page, reading every error as problem details, couldn't parse. The API at `/` takes every path the longer contexts don't, and answers each with its own 404 as problem details.
