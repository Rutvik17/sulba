With an approximate index, Postgres applies a query's `WHERE` to the rows the index scan finds, after it: pgvector's documentation gives the example of a condition that {% $fig.share %} of the rows match, where the default list of {% $fig.ef_search %} candidates leaves {% $fig.matching %} on average. Each of the help desk's services holds from {% $fig.smallest %} to {% $fig.largest %} of its passages, but a question's nearest passages are mostly in its own service: on average, {% $fig.own %} of each validation question's {% $fig.ef_search %} nearest, over the {% $fig.questions %} questions. For {% $fig.none %} of the {% $fig.other %} pairs of a question and one of the other services, none of the question's {% $fig.ef_search %} nearest passages are in that service.

pgvector's iterative index scans go on through the index until the query has its rows, or until they've visited `hnsw.max_scan_tuples` rows, {% $fig.max_scan %} by default: each time, the scan searches the lowest layer again from the candidates the last search left, `ef_search` at a time. In `strict_order` it returns passages in order of distance, and leaves out any it finds nearer than one it has already returned; `relaxed_order` returns those too, slightly out of order, which pgvector's documentation says gives better recall.

A materialized CTE runs its query on its own, before the query around it, which then sorts its rows by distance. Postgres 17 and later take a CTE's `ORDER BY` as the order its rows come out in, so an outer `ORDER BY distance` would sort nothing and leave the relaxed scan's order as it was. `distance + 0` is another expression, which Postgres sorts by, as pgvector's documentation shows.

When a filter takes only a few values, as the services do, pgvector's documentation suggests a partial index for each: an HNSW index built `WHERE (domain = 'va')` holds only that service's passages, so every candidate a search in it finds is in that service.
