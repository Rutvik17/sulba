The secret stays out of sight. Pydantic's `SecretStr` is "A string used for storing sensitive information that you do not want to be visible in logging or tracebacks": its repr and its JSON show asterisks, and the code that needs the secret asks for it by name. The provider's issuer is an `https://` address, as OpenID Connect requires of an issuer, and the desk finds the provider as it starts, so a wrong issuer stops the start rather than the first person to sign in.

Cookies go only over HTTPS when the desk is served over HTTPS. MDN's reference on `Set-Cookie` says `Secure` "Indicates that the cookie is sent to the server only when a request is made with the https: scheme (except on localhost), and therefore, is more resistant to manipulator in the middle (MITM) attacks." The cookies are `SameSite=Lax`, since the provider sends the browser back from another site: the cookies draft says Lax sends cookies "along with cross-site requests if and only if they are top-level navigations which use a "safe" (in the [HTTP] sense) HTTP method", and that `Strict` cookies "will not be sent along with top-level navigations which are triggered from a cross-site document context", so a Strict sign-in cookie would never reach the callback.

Lax alone isn't the whole defence. The same draft says it "provides reasonable defense in depth against CSRF attacks that rely on unsafe HTTP methods (like POST), but does not offer a robust defense against CSRF as a general category of attack." OWASP's Cross-Site Request Forgery Prevention Cheat Sheet suggests Fetch Metadata: "By default, reject non-safe methods (POST / PUT / PATCH / DELETE) when Sec-Fetch-Site: cross-site", and treat same-site the same way unless sibling subdomains are trusted. Where a browser sends no `Sec-Fetch-Site`, the sheet asks for "standard origin verification": "If the Origin header is present, verify that its value matches the target origin." MDN's reference on `Origin` says browsers add it to cross-origin requests, and to same-origin ones "except for GET or HEAD requests", so a POST with neither header doesn't come from a page in a browser, which a cross-site request needs.

The usage is each person's own, as the conversations are: one more `JOIN` keeps the dashboard to the turns of the conversations the person owns.
