The provider's addresses come from the provider itself. OpenID Connect Discovery puts its document at the issuer followed by `/.well-known/openid-configuration`, and says: "The issuer value returned MUST be identical to the Issuer URL that was used as the prefix to /.well-known/openid-configuration to retrieve the configuration information. This MUST also be identical to the iss Claim value in ID Tokens issued from this Issuer." A document that names another issuer isn't the provider the desk was set up for, so nothing in it is used.

PKCE ties the code to this request. The desk keeps the verifier and sends only its challenge; when it exchanges the code, it sends the verifier, and the provider checks that the verifier's challenge is the one it was sent. RFC 7636 asks for a verifier made from "a 32-octet sequence", base64url-encoded "to produce a 43-octet URL safe string", which is what `secrets.token_urlsafe(32)` gives. The S256 challenge is `BASE64URL-ENCODE(SHA256(ASCII(code_verifier)))`. RFC 9700, OAuth's current security advice, says clients "SHOULD use PKCE code challenge methods that do not expose the PKCE verifier in the authorization request", and "Currently, S256 is the only such method." A provider's metadata lists the methods it supports, and RFC 8414 says that when the list is missing, "the authorization server does not support PKCE."

The state comes back with the code, so the desk can tell its own answers from anyone else's, and the nonce comes back inside the ID token. RFC 9700 says the PKCE challenge or nonce "MUST be transaction-specific and securely bound to the client and the user agent in which the transaction was started": a new one for every sign-in, kept where only that browser's sign-in finds it.
