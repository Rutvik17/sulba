A person is their issuer and subject. OpenID Connect Core says the two "used together, are the only Claims that an RP can rely upon as a stable identifier for the End-User", and that "an Issuer MAY re-use an email Claim Value across different End-Users at different points in time, and the claimed email address for a given End-User MAY change over time." The email and name are kept to show, and brought up to date at each sign-in.

The database never holds a token. OWASP's Session Management Cheat Sheet describes this as one-way storage: "A fast hash is sufficient for these random verifiers; password hashing algorithms are unnecessary", and it "protects against read-only disclosure of session records and backups that contain only verifier hashes. It does not protect against stolen cookies, modification of session records, or compromise of the application." The same sheet asks for "at least 64 bits of entropy" in a session id, and each token here is 32 random bytes.

A sign-in is taken once, by the request that finishes it, and a session ends on a set day. OWASP: "All sessions should implement an absolute timeout, regardless of session activity", which "limits the amount of time an attacker can use a hijacked session and impersonate the victim user." The ending is checked in the database, where the client can't move it.

A request without a session gets 403, not 401. HTTP's definition of 401 says "The server generating a 401 response MUST send a WWW-Authenticate header field ... containing at least one challenge applicable to the target resource", and a session cookie isn't one of HTTP's authentication schemes. 403 means "the server understood the request but refuses to fulfill it."
