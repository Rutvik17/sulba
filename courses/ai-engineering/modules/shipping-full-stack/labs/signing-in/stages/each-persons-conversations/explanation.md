The owner is part of the query, not a check after it. A conversation that comes back from `get` is already the person's, so no route can forget to compare. Someone else's conversation answers as one that isn't there: HTTP's definition of 403 says that "An origin server that wishes to "hide" the current existence of a forbidden target resource MAY instead respond with a status code of 404 (Not Found)." A 403 would tell whoever asks that a conversation with that id exists.

The owner refers to `people` with `ON DELETE CASCADE`, which Postgres's documentation describes: "CASCADE specifies that when a referenced row is deleted, row(s) referencing it should be automatically deleted as well." A person who is deleted takes their conversations with them, and those take their messages and turns, by the cascades of Conversations in Postgres.

The list's index matches its query. Postgres's documentation on indexes and `ORDER BY` says: "An important special case is ORDER BY in combination with LIMIT n: an explicit sort will have to process all the data to identify the first n rows, but if there is an index matching the ORDER BY, the first n rows can be retrieved directly, without scanning the remainder at all." With `owner` first, the index finds one person's conversations, already newest first.
