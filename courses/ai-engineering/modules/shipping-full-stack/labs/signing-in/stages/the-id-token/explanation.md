The state is checked first. It came back in the browser's address, so an answer whose state isn't this sign-in's was started somewhere else, and its code is never spent.

OpenID Connect Core lists how a client validates an ID token. "The Issuer Identifier for the OpenID Provider (which is typically obtained during Discovery) MUST exactly match the value of the iss (issuer) Claim." "The Client MUST validate that the aud (audience) Claim contains its client_id value registered at the Issuer identified by the iss (issuer) Claim as an audience", and "The ID Token MUST be rejected if the ID Token does not list the Client as a valid audience, or if it contains additional audiences not trusted by the Client": PyJWT's `strict_aud` holds the audience to the desk's id alone. "The current time MUST be before the time represented by the exp Claim." And "If a nonce value was sent in the Authentication Request, a nonce Claim MUST be present and its value checked to verify that it is the same value as the one that was sent in the Authentication Request."

The signature is checked with "the keys provided by the Issuer", in the algorithm the desk expects. PyJWT's documentation warns: "Do not compute the algorithms parameter based on the alg from the token itself", so `algorithms` is fixed at RS256, and a token whose header says it has no signature is refused. The core specification allows a client to skip the signature for a token "received via direct communication between the Client and the Token Endpoint", relying on TLS; checking it all the same costs one fetch of the keys.

The keys are fetched once and kept. OpenID Connect Core describes how a provider rotates them: "Keys can be rolled over by periodically adding new keys to the JWK Set at the jwks_uri location. The signer can begin using a new key at its discretion and signals the change to the verifier using the kid value. The verifier knows to go back to the jwks_uri location to re-retrieve the keys when it sees an unfamiliar kid value."
