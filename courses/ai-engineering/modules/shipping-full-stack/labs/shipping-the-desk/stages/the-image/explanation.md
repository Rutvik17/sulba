Each stage starts from its own image, and only what's copied out of it reaches the next. Docker's best practices: "Multi-stage builds let you reduce the size of your final image, by creating a cleaner separation between the building of your image and the final output." The desk's image has Python, its packages, its files and the compiled page, and no Node, npm, uv or test packages, so less to download, start and keep patched.

The packages come from the lock. uv's documentation of `--locked`: "Requires that the lockfile is up-to-date. If the lockfile is missing or needs to be updated, uv will exit with an error." The image gets the versions the tests ran, or no image at all. `--no-dev` leaves out the `dev` group, pytest and the test database. uv's Docker guide also suggests `UV_COMPILE_BYTECODE=1`: "Compiling Python source files to bytecode is typically desirable for production images as it tends to improve startup time". Both Python stages use the same image, since the environment's `python` points at the Python it was made with.

Tags move. Docker's best practices: "Image tags are mutable, meaning a publisher can update a tag to point to a new image." A full version such as `python:3.14.9-slim-trixie` stays on one Python release, where `python:3.14-slim` moves to each new one, and a digest never changes, at the cost Docker names: "you're opting out of automated security fixes". Whichever you choose, rebuild the image when its base gets a fix.

The desk runs as a user that isn't root: "If a service can run without privileges, use USER to change to a non-root user." Its `CMD` is in exec form, a JSON list, so `python` is the container's first process and gets the host's SIGTERM. Docker's reference says of the shell form that it starts the program "as a subcommand of /bin/sh -c, which does not pass signals. This means that the executable will not be the container's PID 1, and will not receive Unix signals." Without the signal, the desk's 25 seconds for open requests never start, and the host kills it.

The `HEALTHCHECK` asks `/health`, not `/ready`: a database outage should keep callers away from the desk, not mark the container itself unhealthy. Docker runs it every 30 seconds by default, and "It takes retries consecutive failures of the health check for the container to be considered unhealthy." On Render, the health check is a path you set in the service's settings instead.

Secrets stay out of the image. Docker's build check for them: "setting secrets in a Dockerfile using ENV or ARG is insecure because they persist in the final image." The desk reads its settings from the environment it runs in, which the host sets, so the same image runs on your machine and on Render with different ones.
