`/health` and `/ready` answer two questions. Kubernetes' documentation puts them so: "Liveness probes determine when to restart a container", and "Readiness probes determine when a container is ready to accept traffic." It also warns that "Incorrect implementation of liveness probes can lead to cascading failures", and its advice for an app like the desk is: "When your app has a strict dependency on back-end services, you can implement both a liveness and a readiness probe. The liveness probe passes when the app itself is healthy, but the readiness probe additionally checks that each required back-end service is available." A database that's down is no reason to restart the desk, but it is a reason not to send it callers, who would get only errors.

The model check asks the server whether it's ready rather than asking the model something. llama.cpp's server answers `/health` with 503 and "Loading model" while "the model is still being loaded", and with 200 once it's ready. A question for the model would take a slot a caller could use, at every check.

Each check has two seconds, and they run at once, so `/ready` answers within about two seconds whatever hangs. A host that asks waits only so long: Render, for one, "considers a check successful if the instance responds with a 2xx or 3xx status code within five seconds", and when an instance "fails consecutive health checks for 15 seconds, Render temporarily stops routing traffic to it to give it an opportunity to recover." A check that waited on a stuck database for the pool's or the client's own timeouts would answer too late to say why.
