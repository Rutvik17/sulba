Streaming lets the caller read the reply as the model writes it, rather than wait for all of it. Server-sent events are plain HTTP: a response of type `text/event-stream` whose events are blocks of fields, such as `event:` and `data:`, each block ending at a blank line. FastAPI's `EventSourceResponse` handles the rest. FastAPI's documentation says it sends "a "keep alive" ping comment every 15 seconds when there hasn't been any message, to prevent some proxies from closing the connection", sets `Cache-Control: no-cache`, and sets `X-Accel-Buffering: no` "to prevent buffering in some proxies like Nginx".

The first event is the dividing line for errors. Before it, a request can still fail with a status of its own: a conversation that isn't there, one that's already replying, or a full line. After it, the 200 has been sent, so a failure can only be an event. Each stream ends with `done` or `error`, so a client whose stream ends with neither knows the connection dropped.

A turn is kept only when it's whole. A reply cut off by its time limit or the model's failure is not something the desk said. If it were kept, the model would read half a reply on the next turn, and the conversation would show a message that never ended. The caller's message goes too, so they can send it again.

Only one reply runs in a conversation at a time. Two at once would both add to the same agent's messages, and the model would read them interleaved. RFC 9110's 409 is for a request that "could not be completed due to a conflict with the current state of the target resource", and is "used in situations where the user might be able to resolve the conflict and resubmit the request". Once the reply ends, the caller can send again.
