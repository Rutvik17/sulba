With the schema written as migrations that the app applies itself, every copy of the app reaches the same schema from wherever its database stands. An empty database gets every migration, and one a version behind gets the rest. The record in `schema_migrations` is what makes each migration run once. Its checksum catches a migration edited after it ran: the databases that ran the old SQL and the ones that will run the new SQL would no longer have the same schema, so a change to the schema is always a new migration.

Each migration runs in one transaction with its record. One that fails rolls back with its record, so the next run starts it again from the beginning, rather than from halfway through.

Two copies of the app that start at once, as they do when a host starts several, would each find a migration missing and both apply it, and the second would fail on a table the first had just made. An advisory lock makes them take turns. Postgres's documentation calls these "locks that have application-defined meanings", and says "the system does not enforce their use — it is up to the application to use them correctly": every copy takes the same key before it migrates. "Once acquired at session level, an advisory lock is held until explicitly released or the session ends", so the lock holds across each migration's transaction, and the `finally` releases it on a failure as well.

The tables hold the data to its shape, so a bug in the app can't store a role, page or outcome there isn't, a message at a position already taken, or a message for a conversation that doesn't exist.
