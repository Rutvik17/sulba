Everything the chat puts on the page is text. A reply is a model's words, and its messages can carry whatever a caller typed or a help page said, so none of it goes through `innerHTML`. OWASP's cheat sheet on cross-site scripting: "When displaying text with JavaScript, assign it to the textContent property of an ordinary element such as a `<div>`. This creates a text node without parsing HTML". The same holds for `append` with a string.

The log is a live region. MDN lists `log` among the roles that are live regions already, for a "Chat, error, game or other type of log", and suggests a redundant `aria-live="polite"` "To maximize compatibility". A polite region is read "whenever the user is idle". A reply comes in many small pieces, and a screen reader that read each change would read the reply over and over as it grew. `aria-busy` asks it to wait. MDN: "The aria-busy attribute with a value of true can be added to an element currently being updated or modified, to inform the assistive technology that it should wait until the modifications or changes are complete before exposing the content to the user." Once the reply is done, `aria-busy` goes back to `false`. The status is a live region too, so it says only what went wrong, once.

A turn that fails leaves no trace on the page because it leaves none on the desk: the desk rolls back a turn that doesn't finish, so a page that kept the message would show a conversation the desk doesn't have. The message goes back in the box, so the caller can send it again.

`close()` aborts the reply's request. MDN on `AbortController.abort()`: it "Aborts an asynchronous operation before it has completed. This is able to abort fetch requests, consumption of any response bodies, and streams." The desk sees the connection close and ends the turn, and its place goes to the next caller. The same signal idea stops the form's listener, so a chat that's closed can't send a message for a conversation that's no longer on the page.
