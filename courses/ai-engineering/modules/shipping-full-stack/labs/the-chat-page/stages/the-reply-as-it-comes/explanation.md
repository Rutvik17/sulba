The HTML Standard says how a browser reads an event stream, and the page reads it the same way. "Streams must be decoded using the UTF-8 decode algorithm. The UTF-8 decode algorithm strips one leading UTF-8 Byte Order Mark (BOM), if any. The stream must then be parsed by reading everything line by line, with a U+000D CARRIAGE RETURN U+000A LINE FEED (CRLF) character pair, a single U+000A LINE FEED (LF) character not preceded by a U+000D CARRIAGE RETURN (CR) character, and a single U+000D CARRIAGE RETURN (CR) character not followed by a U+000A LINE FEED (LF) character being the ways in which a line can end."

The network decides where a chunk ends, not the desk. A CR at the end of a chunk could be a whole line ending or the first half of a CRLF, which the next chunk settles, so the reader holds it until then. A character's bytes can be cut too. MDN on `TextDecoder.decode`'s `stream` option: "Set to true if processing the data in chunks, and false for the final chunk or if the data is not chunked." Decoding each chunk on its own would turn the cut character into replacement characters.

The rules for each line are the standard's own. A blank line dispatches the event, but "If the data buffer is an empty string, set the data buffer and the event type buffer to the empty string and return", and "If the data buffer's last character is a U+000A LINE FEED (LF) character, then remove the last character from the data buffer." A line that starts with a colon is ignored: the standard suggests servers send such a comment "every 15 seconds or so", so that proxies don't drop a quiet connection. "If value starts with a U+0020 SPACE character, remove it from value": one space, not every space. And "If the file ends in the middle of an event, before the final empty line, the incomplete event is not dispatched."

`reply` turns the stream's end into an answer either way. A reply ends with `done` or `error`, so a stream that stops without either stopped early, and the page hears that rather than waiting on an answer that won't come. The `signal` goes to `fetch`: MDN says that when a request is aborted after `fetch` has fulfilled, "attempting to read the response body will reject with an AbortError exception." The reader's `cancel()` in `finally` lets the stream go when the page stops reading for its own reasons; MDN: "Calling this method signals a loss of interest in the stream by a consumer."
