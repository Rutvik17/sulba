Every worker draws the epoch's order from the same seed and epoch, so they all hold the same order, and their turns through it never overlap. Orders drawn separately would: with {% $fig.workers %} workers each taking `$1/\fig{workers}$` of the records at random, a record is missed by all of them with probability `$(1 - 1/\fig{workers})^{\fig{workers}}$`, so about {% $fig.missed %} of the records would be left out of every epoch. PyTorch's `DistributedSampler`, which gives each process a share exclusive to it, needs the same seed on every process.

Taking turns record by record keeps the shares within one record of each other, and carrying the order on makes them equal: the {% $fig.records %} records on {% $fig.workers %} workers give each {% $fig.share %}, with {% $fig.again4 %} record used twice. Shares one record apart can still need different numbers of batches. Without the order carried on, {% $fig.uneven %} workers would hold {% $fig.big %} or {% $fig.small %} records, which in batches of {% $fig.uneven_size %} take {% $fig.big_batches %} or {% $fig.small_batches %} steps. `np.resize` carries an array on from its start to any length, so it also covers more workers than records, where adding `order[:extra]` falls short.

`np.random.default_rng([seed, epoch])` mixes both numbers through a `SeedSequence`, so every pair gets its own stream. `DistributedSampler` seeds its generator with `seed + epoch`, so a run with seed 1 shuffles its first epoch the way a run with seed 0 shuffles its second: runs with nearby seeds share their orders, an epoch apart.
