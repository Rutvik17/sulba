A chunk of `$r$` new samples against `$n$` records of `$d$` measurements makes `$r \times n \times d$` differences of 8 bytes each, and squaring them makes as many again before the sum shrinks them to `$r \times n$` numbers. Sized to the whole budget, a chunk is {% $fig.naive_rows %} rows: {% $fig.naive_mb %} MB of differences and {% $fig.naive_mb %} MB of squares, twice the budget. In a loop, the last chunk's arrays also stay alive while the next chunk's are made, until their names are given the new ones. CPython, the Python the lab runs on, frees most objects, arrays among them, as soon as nothing refers to them, so the arrays a function makes for itself are freed when it returns.

Sized to a quarter of the budget, a chunk is {% $fig.rows %} rows: {% $fig.chunk_mb %} MB of differences, as much for their squares, and the standardized records' {% $fig.records_mb %} MB beside them. The chunks don't change the answer. Each new sample's distances are its own row, so splitting the rows into chunks changes how many are worked on at once, not which records they find.

Memory and time trade against each other. One row at a time stays far inside the budget, at the cost of a Python loop of {% $fig.lookups %} steps; the whole batch at once is a single step that needs {% $fig.full_mb %} MB. Chunks sized from the budget take as few steps as the memory allows.
