# 38. Test a lab's sign-in against a scripted OpenID provider

- Status: accepted
- Date: 2026-10-22

## Context

Intermediate's Shipping full stack module signs the users of a web app in with OpenID Connect: the app sends the browser to a provider, the person signs in there, and the provider sends the browser back with a code, which the app exchanges for an ID token and checks. The lab runs on the learner's machine (record 28), and its tests must give the same result on every machine, with no account, network, browser or money. What the lab teaches is mostly what the app refuses: a token for another app, from another issuer, out of date or signed with another key, a code used twice, a state that doesn't match. A real provider never gives those on cue.

## Decision

- **The `identity` fixture:** a scripted OpenID provider, in `sulba_fixtures.py` with the runner's other fixtures. Its issuer is `https://id.test`, it knows one client, `desk`, with a secret and the redirect URI `https://desk.test/auth/callback`, and two people, Ada and Grace, whose subjects are `user-ada` and `user-grace`. `identity.person(name, email=...)` adds others.
- **The browser's part:** the test plays the browser. `identity.sign_in(url, name)` takes the app's authorization request and gives the address the provider sends the browser back to, the redirect URI with a code and the request's state, and `identity.declines(url)` the same address with `access_denied`. A request from a client it doesn't know, or to a redirect URI not registered for it, raises `ValueError`, since a provider shows an error rather than redirect there. One without `openid` in its scope, `code` as its response type and an S256 code challenge comes back with `invalid_request`.
- **The provider's endpoints:** discovery, its keys as a JSON Web Key Set, the token endpoint and userinfo, which code reaches through httpx: `identity.client()` and `identity.async_client()` give clients whose base URL is the issuer, over httpx's `MockTransport`, as the `model` fixture does (record 31). The token endpoint takes the client's secret by HTTP Basic or in the form, gives each code once, to the redirect URI it was given for and the verifier its challenge came from, and answers otherwise with `invalid_client` (401, with a `WWW-Authenticate` challenge) or `invalid_grant` (400). Tokens come with `Cache-Control: no-store` and `Pragma: no-cache`. Userinfo refuses an access token it didn't give with 401 and `WWW-Authenticate: Bearer error="invalid_token"`.
- **ID tokens:** JWTs signed with RS256 by a 2,048-bit RSA key its keys endpoint publishes, with `iss`, `aud`, `sub`, `email`, `name`, `iat`, `exp` five minutes on by the system's clock, and the request's nonce.
- **Tokens to refuse:** `identity.id_token(name, audience=..., issuer=..., lasts=..., nonce=..., stranger=True)` makes a token of any of those shapes, a stranger's signed with a key the provider doesn't publish, and `identity.returns(**fields)` puts fields of the test's in the token endpoint's next answer. `identity.rotate()` signs with a new key from then on, published beside the old one.
- **What was sent:** `identity.requests` keeps every request to its endpoints, with its headers and form.
- **Checking tokens:** a lab's code uses PyJWT 2.15.1, with cryptography, which its project locks. Pyodide has no build of PyJWT, so `pyjwt` joins the packages only a machine lab loads. PyJWT's `PyJWKClient` fetches keys through urllib, which can't reach the scripted provider, so code fetches them with its httpx client and reads them with `jwt.PyJWKSet.from_dict`.

## Options

| Option | What it does well | Where it falls short |
| --- | --- | --- |
| A scripted provider over httpx's `MockTransport`, as a fixture (chosen) | The same result on every machine; no account, network or browser; tokens of every shape a check must refuse, on cue; beside the `model` fixture, in the runner | Code takes its httpx client from the test; it holds requests only to the rules it scripts, so a real provider's own, such as its limits on unverified apps, meet the learner only when they register one |
| A real provider, such as Google or GitHub | What the learner's users sign in with | An app registered with the provider, a person signing in in a browser and the network for every run, and credentials in CI; it can't give a bad token on cue; GitHub's OAuth apps give no ID token |
| mock-oauth2-server, NAV's scriptable server | The authorization code flow with PKCE, and signed tokens checked through discovery and keys, as a real provider's are | Runs on the JVM or in Docker, which a lab's project can't install |
| oidc-provider, Filip Skokan's server | OpenID Certified, with PKCE and many other specifications | Runs on Node, which a lab's project can't install, and is configured as a server is, not scripted by a test |
| Patching the app's function that checks a token | Short tests | Tests nothing of the flow: the state, the nonce, PKCE, the exchange and the token's checks are what the lab teaches |

For checking tokens in a lab's code:

| Option | What it does well | Where it falls short |
| --- | --- | --- |
| PyJWT 2.15.1 (chosen) | One call checks a token's signature, audience, issuer and expiry; reads a key set; its documentation shows an OpenID Connect sign-in; MIT | `PyJWKClient` fetches through urllib, so code fetches the keys itself |
| Authlib 1.9.1 | Starlette and FastAPI clients that keep the state, the PKCE verifier and the nonce in the session and check the ID token | Does out of sight the steps the lab teaches; its README says it will deprecate `authlib.jose` for joserfc |
| joserfc 1.7.7 | JWS, JWE, JWK and JWT, from Authlib's author; BSD-3-Clause | `decode` checks the signature, and the claims are checked in a second step with a `JWTClaimsRegistry`, so code that stops at `decode` accepts a token for any audience |

## Evidence

- [OpenID Connect Core 1.0](https://openid.net/specs/openid-connect-core-1_0.html), section 3.1.3.7, ID Token Validation: the issuer "MUST exactly match the value of the iss (issuer) Claim", the client "MUST validate that the aud (audience) Claim contains its client_id value registered at the Issuer identified by the iss (issuer) Claim as an audience", "The current time MUST be before the time represented by the exp Claim", and "If a nonce value was sent in the Authentication Request, a nonce Claim MUST be present and its value checked to verify that it is the same value as the one that was sent in the Authentication Request." On the signature: "If the ID Token is received via direct communication between the Client and the Token Endpoint (which it is in this flow), the TLS server validation MAY be used to validate the issuer in place of checking the token signature." The alg "SHOULD be the default of RS256".
- [RFC 6749](https://www.rfc-editor.org/rfc/rfc6749), OAuth 2.0: "The client MUST NOT use the authorization code more than once" (4.1.2). "If the request fails due to a missing, invalid, or mismatching redirection URI, or if the client identifier is missing or invalid, the authorization server SHOULD inform the resource owner of the error and MUST NOT automatically redirect the user-agent to the invalid redirection URI" (4.1.2.1). The token endpoint must "ensure that the "redirect_uri" parameter is present if the "redirect_uri" parameter was included in the initial authorization request as described in Section 4.1.1, and if included ensure that their values are identical" (4.1.3), and "MUST include the HTTP "Cache-Control" response header field [RFC2616] with a value of "no-store" in any response containing tokens, credentials, or other sensitive information, as well as the "Pragma" response header field [RFC2616] with a value of "no-cache"" (5.1). Section 5.2 answers an error with 400 "(unless specified otherwise)", `invalid_grant` for a code that "does not match the redirection URI used in the authorization request, or was issued to another client", and for `invalid_client`: "If the client attempted to authenticate via the "Authorization" request header field, the authorization server MUST respond with an HTTP 401 (Unauthorized) status code and include the "WWW-Authenticate" response header field matching the authentication scheme used by the client."
- [RFC 7636](https://www.rfc-editor.org/rfc/rfc7636), PKCE: `code_challenge = BASE64URL-ENCODE(SHA256(ASCII(code_verifier)))` for S256, which the server checks at the token endpoint.
- [RFC 9700](https://www.rfc-editor.org/rfc/rfc9700), OAuth 2.0 Security Best Current Practice, section 2.1: "the PKCE challenge or OpenID Connect nonce MUST be transaction-specific and securely bound to the client and the user agent in which the transaction was started", "Currently, S256 is the only such method", and "Authorization servers MUST support PKCE [RFC7636]."
- OpenID Connect Core's UserInfo Error Response is "an Error Response as defined in Section 3 of OAuth 2.0 Bearer Token Usage [RFC6750]", whose example is a 401 with `WWW-Authenticate: Bearer error="invalid_token"`. [RFC 6750](https://www.rfc-editor.org/rfc/rfc6750), section 3: a resource server refusing a request without a valid token "MUST include the HTTP "WWW-Authenticate" response header field".
- [OpenID Connect Discovery 1.0](https://openid.net/specs/openid-connect-discovery-1_0.html) for the discovery document's fields, and [RFC 7517](https://www.rfc-editor.org/rfc/rfc7517) for a JSON Web Key Set.
- PyJWT 2.15.1's [usage](https://pyjwt.readthedocs.io/en/stable/usage.html), whose OIDC Login Flow fetches the discovery document and decodes the ID token with `audience=client_id` and the algorithms the provider supports, and its [API](https://pyjwt.readthedocs.io/en/stable/api.html), on `PyJWKSet`, `PyJWKClient` and `decode`, which warns: "Do not compute the algorithms parameter based on the alg from the token itself". PyJWT's `jwks_client.py` fetches with `urllib.request`.
- Authlib's [FastAPI client](https://docs.authlib.org/en/stable/oauth2/client/web/fastapi.html) and [web clients](https://docs.authlib.org/en/stable/oauth2/client/web/index.html) pages, 1.9.1, and its README on `authlib.jose`. joserfc's [JWT guide](https://jose.authlib.org/en/guide/jwt/): "usually you will use the claims registry after ``.decode``". PyPI's pages for [PyJWT](https://pypi.org/project/PyJWT/), [Authlib](https://pypi.org/project/Authlib/) and [joserfc](https://pypi.org/project/joserfc/).
- GitHub's [Authorizing OAuth apps](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps): a user's identity comes from `GET https://api.github.com/user` with the access token, and the page describes no ID token. [Google's discovery document](https://accounts.google.com/.well-known/openid-configuration) gives RS256 ID tokens and S256 among its code challenge methods.
- [mock-oauth2-server's README](https://github.com/navikt/mock-oauth2-server): "Scriptable OAuth2/OpenID Connect server for JVM tests and Docker Compose", with the authorization code flow "with PKCE (`plain` and `S256`)". [oidc-provider's README](https://github.com/panva/node-oidc-provider): an npm package for Node, OpenID Certified, implementing RFC 6749, OIDC Core 1.0 and RFC 7636 among others.
- Pyodide 314.0.7's lock file has cryptography 47.0.0 and no PyJWT, joserfc or Authlib.
- The fixture's tests sign a person in, check the ID token with PyJWT against the keys endpoint, and show each refusal above: a reused code, a wrong verifier or redirect URI, a wrong secret, an unknown client or redirect, a request without S256 or `openid`, a token for another audience or issuer, out of date or a stranger's, and a token signed before and after a rotation.

## Why

The scripted provider is the only option a lab's project can run with nothing more than uv, and the only one that gives, on cue, each token the lab's code must refuse. It holds the app to the rules of RFC 6749, RFC 7636 and OpenID Connect Core that the lab teaches, and it speaks httpx like the `model` fixture, so a lab's tests build both the same way. PyJWT checks a token's claims in the same call that checks its signature, which leaves the learner to write the flow's other steps: the state, the nonce, PKCE and the exchange, which are the lab. The strongest case against: code that passes against a script has never met a real provider, whose discovery document, errors and limits differ from the script's. Code that reads every address from the provider's discovery document, which OpenID Connect Discovery defines, meets a real provider with other settings, not other code.

## Consequences

A lab's code takes its httpx client from its caller, and fetches the provider's keys itself rather than through `PyJWKClient`. The ID tokens' times come from the system's clock, as PyJWT reads it, so a test of a token out of date makes one with a negative lifetime rather than moving a clock. The provider gives no refresh tokens and no logout, and serves only the authorization code flow, so a lab that needs more adds it here. Making the RSA keys takes a moment, so each is made once a run.

## Revisit when

A lab teaches another flow or a refresh token, Pyodide ships PyJWT, or a lab needs its sign-in to meet a real provider in its tests.
