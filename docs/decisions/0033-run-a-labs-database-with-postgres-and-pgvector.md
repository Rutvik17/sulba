# 33. Run a lab's database on the learner's machine with Postgres and pgvector

- Status: accepted
- Date: 2026-10-20

## Context

The Retrieval module's labs keep embeddings in Postgres and search them with pgvector. Their tests need a real server with pgvector, and so does a learner's own code. Sulba runs no learner code (record 17), so the server runs on the learner's machine, from the lab's download (record 28): on Windows or Linux on x86-64, Linux on Arm, or macOS 14 or later on Apple silicon, without administrator rights, an account or money. It has to be pinned like every other file a lab uses (record 29), give each test a database of its own, and run the same way in CI.

## Decision

- **The server:** PostgreSQL 18.6 from the embedded-postgres 18.6.3 wheel, which a lab's project locks with uv like any other package. The runner (`sulba_fixtures.py`) starts it with the wheel's own initdb and pg_ctl, listening only on 127.0.0.1, with SCRAM-SHA-256 and a password it makes, in UTF-8 with the builtin C.UTF-8 locale whatever the system's.
- **pgvector:** on macOS and Windows, the 0.8.6 that comes with the wheel. On Linux, 0.8.7 from the PostgreSQL project's packages for Debian 12, pinned in the runner by size and sha256 for x86-64 and for Arm, fetched from apt.postgresql.org the first time into `sulba` in the learner's cache folder (record 32), and loaded through `extension_control_path` and `dynamic_library_path`.
- **Tests:** the `database` fixture gives each test a new database, made from a template with pgvector installed, on one server per run at a free port. The server stops and its files are deleted when the run ends.
- **The learner's database:** `uv run sulba.py db` starts a server at port 5432 until Ctrl+C, and `--port` takes another. Its data stays in the download's `.sulba/database`, and its password in `.sulba/database-password`, readable by the learner alone where the system allows it.
- **When it can't start:** the runner says why. The reasons are running as root, which Postgres refuses; on Windows, a processor without AVX2, which the wheel's pgvector needs; or on Windows, a folder whose name has a character the system's code page lacks, since Postgres's programs take their paths in it.
- **CI:** the Machine labs jobs run a fixture lab whose test uses the database on Windows, macOS and Linux, and the lab package's tests start the fixture's server and the `db` command on Linux.

## Options

| Option | What it does well | Where it falls short |
| --- | --- | --- |
| embedded-postgres 18.6.3, with the PostgreSQL project's pgvector on Linux (chosen) | Postgres 18.6; COPY, HNSW and IVFFlat indexes, full-text search and connections kept apart, on all five systems the spike ran; built from upstream sources by a public workflow; Apache License 2.0 | Started in September 2026, by one author; its pgvector needs AVX2 on Windows and SVE on Linux on Arm, so Linux takes pgvector from the PostgreSQL project; pgvector 0.8.6 on macOS and Windows |
| pixeltable-pgserver 0.6.0 | From Pixeltable, Inc.; passed the same checks on Linux and macOS | Its pgvector for Windows needs AVX-512, and the server stopped at the first cosine distance on GitHub's Windows runner; Postgres 18.4; pgvector 0.8.5 |
| PGlite 0.5.10 behind pglite-socket, on Node | Postgres in WebAssembly, which runs on any processor; pgvector 0.8.7, and BM25 through pg_textsearch | One session shared by every connection; no COPY; a second connection refused; CREATE DATABASE drops the connection; 10,000 vectors take 22 to 33 seconds to load; needs Node |
| pgvector's Docker image | Built by pgvector's author to run on any processor | Needs Docker, which a lab's project can't install, and a Linux container on Windows and macOS |
| A hosted Postgres, such as a free Supabase or Neon project | Real Postgres with pgvector, with nothing to install | An account and a network for every run; a free plan's limits; the learner's data leaves their machine; CI would need credentials |

## Evidence

- The spike ran each candidate on five of GitHub's runners: Linux on x86-64 and on Arm, macOS 14 and 15 on Apple silicon, and Windows Server 2025. Each loaded 10,000 vectors of 1,024 dimensions, timed 100 exact searches, built HNSW and IVFFlat indexes and measured their recall of the exact top 10, and checked that connections stay apart. embedded-postgres passed everything on all five: loading by COPY took 0.33 to 1.23 seconds, an HNSW index 3.05 to 3.91 seconds, and HNSW with `ef_search` at 40 found 99 to 100 percent of the exact top 10. pixeltable-pgserver passed on Linux and macOS, and on Windows its server closed the connection at the first cosine-distance query. PGlite shared one session between connections: a setting made in one was seen by the next, prepared statements collided ("prepared statement "_pg3_0" already exists"), a second connection at once was refused, CREATE DATABASE dropped the connection and COPY failed. Loading by INSERT took it 21.9 to 32.8 seconds.
- Each build's pgvector, disassembled with llvm-objdump 18: pixeltable-pgserver's `vector.dll` for Windows runs AVX-512 instructions, AVX-512 FP16's among them, in functions it calls without checking the processor, `cosine_distance` among them. embedded-postgres's runs AVX2, FMA and F16C instructions in such functions on Windows and on Linux on x86-64. Both wheels' `vector.so` for Linux on Arm runs SVE instructions in `vector_l2_squared_distance` and others, so it runs only on processors with SVE. The PostgreSQL project's builds for Debian 12 run AVX only in functions chosen after a `cpuid` check of the processor, and the one for Arm runs no SVE.
- [pgvector's README at v0.8.7](https://github.com/pgvector/pgvector/blob/v0.8.7/README.md#portability): "By default, pgvector compiles with `-march=native` on some platforms for best performance. However, this can lead to `Illegal instruction` errors if trying to run the compiled extension on a different machine." Its [Makefile](https://github.com/pgvector/pgvector/blob/v0.8.7/Makefile) sets `OPTFLAGS = -march=native` except on macOS on Arm, and its [Dockerfile](https://github.com/pgvector/pgvector/blob/v0.8.7/Dockerfile) builds with `make OPTFLAGS=""`.
- PyPI's provenance for both wheels names the GitHub workflow that built them, `build-and-test.yml`. [embedded-postgres's](https://github.com/kainpl/embedded-postgres/blob/main/.github/workflows/build-and-test.yml) builds Postgres and pgvector on GitHub's runners: ubuntu-latest, ubuntu-24.04-arm, macos-latest, macos-15-intel and windows-2022.
- [The PostgreSQL project's index for bookworm-pgdg](https://apt.postgresql.org/pub/repos/apt/dists/bookworm-pgdg/main/) lists postgresql-18-pgvector 0.8.7-1.pgdg12+1 at 273,916 bytes for amd64 and 243,408 for arm64, depending on `libc6 (>= 2.14)` and `libc6 (>= 2.17)`.
- [PostgreSQL 18's client settings](https://www.postgresql.org/docs/18/runtime-config-client.html): `extension_control_path` is "A path to search for extensions, specifically extension control files (name.control). The remaining extension script and secondary control files are then loaded from the same directory where the primary control file was found." With `dynamic_library_path`, "If a dynamically loadable module needs to be opened and the file name specified in the CREATE FUNCTION or LOAD command does not have a directory component (i.e., the name does not contain a slash), the system will search this path for the required file." [initdb](https://www.postgresql.org/docs/18/app-initdb.html): "Since the server cannot be run as root, you must not run initdb as root either. (It will in fact refuse to do so.)"
- The runner's database tests passed on the same five runners, Linux on Arm among them with the PostgreSQL project's pgvector 0.8.7, which the server on Linux reported, loaded from the cache folder. The `db` command's test sends Ctrl+C as a POSIX signal, so it ran on all but Windows.
- In a 4-CPU container, embedded-postgres's server on Linux, started with those two settings, installed the PostgreSQL project's pgvector 0.8.7 from a folder of its own, with the control file naming the library without a folder, built HNSW and IVFFlat indexes over 2,000 vectors, and mapped that folder's `vector.so`.
- [pgvector's changelog](https://github.com/pgvector/pgvector/blob/v0.8.7/CHANGELOG.md) for 0.8.7: "Fixed buffer overflow with IVFFlat index build". [Its issue 1036](https://github.com/pgvector/pgvector/issues/1036): "A database user with the ability to create an IVFFlat index can write data out-of-bounds", "Versions Affected: 0.8.6 and below", tracked as CVE-2026-103484. The fix checks each value's dimensions against the index's as the index is built, and computes the size of the index's lists with `mul_size`, which raises an error where the multiplication would overflow.
- Microsoft's [IsProcessorFeaturePresent](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-isprocessorfeaturepresent): `PF_AVX2_INSTRUCTIONS_AVAILABLE`, 40, "The AVX2 instruction set is available", supported "by Windows 10, Version 2004 (May 2020 Update) or later".
- On Windows Server 2025, whose code page was Windows-1252, initdb couldn't open its password file in a folder named "Łódź 🚲", which its message gave as "L�dz ??". In a folder named "Dossier de données é" it ran.

## Why

embedded-postgres is the only wheel whose server and pgvector passed every check on all five systems, and a wheel is what a lab's project can lock, so the download installs the database with the rest of the lab and CI tests the files learners run. Its pgvector, like pixeltable-pgserver's, is built for the processor of the runner that built it, as pgvector's Makefile does unless told otherwise. On Linux on Arm that leaves out every processor without SVE, so on Linux the runner takes the PostgreSQL project's own build, the one its repository serves to Debian and Ubuntu machines, whose disassembly shows no such instruction outside a checked path. PGlite runs on any processor but isn't a server: the labs teach COPY, indexes and connections that stay apart, which it doesn't give. The strongest case against: embedded-postgres is new and has one author, and its pgvector on Windows still needs AVX2, which the runner checks before it starts. On macOS and Windows its pgvector is 0.8.6, below the fix for CVE-2026-103484. The fix checks that each value has the index's dimensions and that the size of the index's lists can't overflow, and the labs' tables have columns of a fixed dimension and IVFFlat indexes far below that size.

## Consequences

A database lab's first run on Linux fetches about 270 KB from apt.postgresql.org, and later runs, in any lab, use the copy in the cache folder. If the PostgreSQL project takes the package down, the fetch fails until the pin moves; CI's Machine labs job on Linux fetches it on every run, so it fails first. On Windows, a processor without AVX2 can't run a database lab's tests or its `db` command, and a lab in a folder whose name the code page can't write has to move. pgvector is 0.8.7 on Linux and 0.8.6 elsewhere, so the labs use nothing that differs between the two. An HNSW index can find other neighbours each time it's built, as its recall differed between two servers on the same runner in the spike, so no figure comes from an approximate index's results. The server has no TLS, as embedded-postgres's Linux build links no OpenSSL, so it answers only on 127.0.0.1. Moving pgvector to 0.8.7 on macOS and Windows waits on a new embedded-postgres release.

## Revisit when

embedded-postgres or another maintained wheel ships a pgvector built to run on any processor, PGlite serves connections that stay apart and takes COPY, or a lab needs an extension the wheel lacks.
