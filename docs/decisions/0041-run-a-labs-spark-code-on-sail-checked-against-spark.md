# 41. Run a lab's Spark code on Sail, and check it against Spark

- Status: accepted
- Date: 2026-10-22

## Context

The Data pipelines module teaches Spark's DataFrame API and Spark SQL on a customer's messy data. Sulba runs no learner code (record 17), so Spark runs on the learner's machine, from the lab's download, installed by uv (record 28): on Windows or Linux on x86-64, Linux on Arm, or macOS 14 or later on Apple silicon, the machines Intermediate names. It has to install without administrator rights, start quickly enough for a test run, read and write files on every one of those systems, give the same results on each, and run the same way in CI. What the learner writes has to be PySpark as Spark runs it.

## Decision

- **The engine:** Sail 0.7.2, an engine in Rust that serves Spark Connect, with PySpark's client 4.2.0, the pair Sail's Getting Started installs, and pandas 2.3.3. A lab's project locks the three, and a stage that imports pyspark lists `pyspark-client` under `packages`. No Java is installed.
- **Tests:** the `spark` fixture gives a test a Spark session. The run starts one Sail server in its own process, on 127.0.0.1 at a free port, which its tests share, with two partitions and the session's time zone UTC, and stops it when they're done. Each test's temporary views are dropped when it ends. The runner sets `SPARK_HOME` to the client's folder before any test file loads, since PySpark's testing helpers exit without it.
- **Checking against Spark:** `pnpm check:machine --spark`, which CI's Spark job runs on Linux, runs each lab whose project locks Sail from its download on Spark 4.2.0 itself, in local mode with two partitions, on the Java 21 in GitHub's Ubuntu image. The download's project takes PySpark in place of Sail and the client, resolved afresh, and each stage's solution must pass there too. Deploys wait for it.
- **What stages keep to:** behaviour that Sail and Spark share. A CSV a stage reads has as many fields in each row as its header. Integer sums stay within their type. Tests check an exception's class, never its message, compare floats with a tolerance, and compare timestamps as strings formatted in Spark.
- **CI:** the Machine labs jobs run the fixture course's Ledger, whose first stage has a test on the `spark` fixture, on Windows, macOS and Linux, and the Spark job runs it on Spark.

## Options

| Option | What it does well | Where it falls short |
| --- | --- | --- |
| Sail with PySpark's client, checked against Spark in CI (chosen) | Wheels for every system Intermediate names, installed by uv with no Java; a session in 1.8 to 5.3 seconds; Spark Connect's PySpark API unchanged; Apache License 2.0 | Differs from Spark in places, among them ragged CSV rows, integer overflow, some result types and every error message; beta, with a release every few weeks; no build for Windows on Arm |
| PySpark 4.2.0 with a Temurin 21 JRE the runner fetches | Is Spark; a JRE for every system, Windows on Arm included | On Windows, every write of a file fails without `winutils.exe`, which Apache doesn't publish; a 450 MB source package built on install; 4.4 to 15.5 seconds to start |
| Spark Connect's client with a JVM Spark server | The same API as Sail, run by Spark | Needs the same JVM, jars and Windows files as the option above |
| DuckDB's Spark API | Wheels for every system | Experimental and to be deprecated; DuckDB's SQL, not Spark's; no `Window` |
| Polars or plain DuckDB | Fast, with wheels for every system | Not PySpark, so the module wouldn't teach Spark |

## Evidence

- A spike ran 24 cases on Sail 0.7.2 and on PySpark 4.2.0 with Temurin 21.0.12.1 on six of GitHub's runners: Linux on x86-64 and on Arm, Windows Server 2025, Windows 11 on Arm, macOS 15 on Apple silicon and on Intel. Spark ran every case on all six; its session took 4.4 to 15.5 seconds to start and the 24 cases 15 to 52 seconds. Sail ran on five, taking 1.8 to 5.3 seconds to start and 2.0 to 5.7 for the cases. On Windows 11 on Arm, uv had no wheel of grpcio 1.84.0, built it from source, and MSVC's compiler failed.
- On both Windows runners, Spark failed to write Parquet. A second run on Linux, Windows and macOS read every Java cause: on Windows, writing Parquet, CSV and JSON each failed with `java.io.FileNotFoundException: HADOOP_HOME and hadoop.home.dir are unset.`, while reads and SQL passed. [Hadoop's wiki](https://cwiki.apache.org/confluence/display/HADOOP2/WindowsProblems): "Hadoop requires native libraries on Windows to work properly -that includes to access the file:// filesystem, where Hadoop uses some Windows APIs to implement posix-like file access permissions." and "This is implemented in HADOOP.DLL and WINUTILS.EXE." [Spark's Windows notes for SparkR](https://raw.githubusercontent.com/apache/spark/v4.2.0/R/WINDOWS.md) point to builds of them that "are not official ASF artifacts".
- Sail and Spark gave the same result in 11 of the 24 cases on every system where both ran: a join with aggregates, SQL with a CTE and a window, null ordering, `try_cast`, aggregate types, UTC timestamps, `fillna`, deduplication by `row_number`, a Parquet round trip and `split` with `explode_outer`. They differed in 13. Sail failed to read a CSV with a row of 6 fields under a header of 5 in every mode ("incorrect number of fields for line 6, expected 5 got 6"), where Spark read it. `2147483647 + CAST(1 AS INT)` gave -2147483648 on Sail, where Spark raised `ARITHMETIC_OVERFLOW` with `spark.sql.ansi.enabled` true on both. `bround` of a decimal, decimal multiplication and `unionByName` with a missing column gave other types. A bad date, a bad cast, a division by zero and an unknown column raised the same classes with other messages. A standard deviation of 1,000 doubles differed in its last digits.
- In this repository's trial, with the time zone set to America/Los_Angeles and the session's time zone UTC, `TIMESTAMP '2026-03-29 01:30:00'` came back from both engines as `datetime(2026, 3, 28, 18, 30)` and, cast to a string, as `'2026-03-29 01:30:00'`.
- [Sail's Getting Started](https://docs.lakesail.com/sail/latest/introduction/getting-started/) installs `pysail==0.7.2` and `pyspark-client==4.2.0`: "Sail can serve as a drop-in replacement for the compute engine behind PySpark applications. The Spark client session communicates with the Sail server using the Spark Connect protocol." Its [API page](https://docs.lakesail.com/sail/latest/reference/python/api/pysail.spark.SparkConnectServer.html) gives `SparkConnectServer(ip='127.0.0.1', port=0)`, `start()`, `stop()` and `listening_address`. [Why Sail](https://docs.lakesail.com/sail/latest/introduction/why-sail/): "If there is a behavior mismatch between Sail and Spark, we consider it a bug." [Migrating from Spark](https://docs.lakesail.com/sail/latest/introduction/migrating-from-spark/): "Error messages returned by Sail may differ from those in Spark." [Its configuration](https://docs.lakesail.com/sail/latest/reference/configuration/) sets `execution.default_parallelism` through `SAIL_EXECUTION__DEFAULT_PARALLELISM`: "If the value is 0, the parallelism is determined based on the number of available CPU cores." Telemetry's exports default to false.
- PyPI's files for [pysail 0.7.2](https://pypi.org/project/pysail/0.7.2/) are abi3 wheels for macOS on x86-64 and Apple silicon, Linux on x86-64 and Arm, and Windows on x86-64, and its classifier is "Development Status :: 4 - Beta". [Sail's changelog](https://docs.lakesail.com/sail/latest/reference/changelog/) dates 0.7.2 September 29, 2026, after 0.7.1 on August 24 and 0.7.0 on August 3, and lists breaking changes in 0.7.0, 0.6.0, 0.5.0, 0.3.0 and 0.2.0.
- [PySpark's installation page](https://spark.apache.org/docs/latest/api/python/getting_started/install.html): "The Python Spark Connect client is a pure Python library that does not rely on any non-Python dependencies such as jars and JRE in your environment." With pandas 3, the client warned: "PySpark does not yet fully support pandas >= 3.0.0. Some features may not work correctly. It is recommended to use pandas < 3.0.0 for now." Without `SPARK_HOME`, importing `pyspark.testing` printed "Could not find valid SPARK_HOME" and exited; with it set to any folder, the tests ran.
- [Spark 4.2.0's documentation](https://spark.apache.org/docs/4.2.0/): "Spark runs on Java 17/21/25". [GitHub's Ubuntu 24.04 image](https://github.com/actions/runner-images/blob/main/images/ubuntu/Ubuntu2404-Readme.md), version 20261012.334.1, holds Java 21.0.12+1 at `JAVA_HOME_21_X64`.
- In this repository, the runner's tests ran the `spark` fixture on Sail in 1.9 seconds and on Spark, with PySpark 4.2.0 on OpenJDK 21.0.12.1, in 18.1 seconds, with the same results.

## Why

Sail is the only option that installs with uv alone on every system Intermediate names and writes files on all of them, and it runs the PySpark a learner will meet at work: the DataFrame API and Spark SQL through Spark Connect. Spark itself can't write a file on Windows without binaries Apache doesn't publish, which the runner would have to fetch from a third party. What Sail gives up is being Spark, and the spike found differences in exactly the messy data the module is about. So Spark stays the reference: CI runs every Spark stage on it, as the References job runs a library's own results (record 27), and a stage that passes on Sail but not on Spark fails the build. The strongest case against: Sail is beta, and a learner's own code that strays outside what the stages cover can meet a difference no check catches.

## Consequences

A Spark lab's project installs about 155 MB of wheels on Linux, among them Sail's 57 to 69 MB. Windows on Arm can't run it, as it can't run Intermediate's PyTorch labs. A stage can't teach a ragged CSV's rows through Spark's reader, ANSI overflow, or Spark's error messages, since Sail differs there; the stages that need such data repair it in DataFrame code from columns read as strings. CI's Spark job builds PySpark's 450 MB source package on each run. Each Sail release is moved to only when the Spark job passes on it, and the pair stays on the client version Sail's documentation names.

## Revisit when

Sail ships a release that reads ragged CSV rows as Spark does and raises on overflow, Spark writes files on Windows without Hadoop's native binaries, or a lab needs part of Spark that Sail lacks, such as RDDs.
